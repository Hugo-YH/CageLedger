# 部署与运行

本页面向部署人员和系统管理员，按「选择运行方式 → 配置数据与账号 → 启动 → 验证 → 升级恢复」组织。生产推荐使用固定版本的 ARM64 镜像；开发体验从[本地开发](/development/local-development)开始。首次部署完成后，应能在同一地址访问门户、工作区、文档和健康检查。

## 选择运行方式

| 场景             | 页面与 API                           | 运行依赖                             | 数据库默认位置                             |
| ---------------- | ------------------------------------ | ------------------------------------ | ------------------------------------------ |
| 开发             | Vite `5173`，API `5174`，文档 `5175` | Node.js 22.x、Python 3.13 与开发依赖 | `data/database/cageledger.sqlite`          |
| 本地生产／源码包 | Python `5173` 同时提供页面与 API     | Python 3.13、生产依赖与文档转换器    | `data/database/cageledger.sqlite`          |
| Docker／群晖     | 容器 `5173` 同时提供页面与 API       | Docker、Compose；容器内依赖已备好    | 镜像显式配置 `/app/data/cageledger.sqlite` |

生产服务提供门户 `/`、工作区 `/app`、文档 `/docs/` 和 `/api`。当前生产设备为 DS223（aarch64），新镜像只构建 `linux/arm64`，历史 AMD64 制品继续保留。

## Docker Compose 部署

### 1. 准备目录、配置和版本

确保目标主机可访问 Gitea 仓库与镜像仓库，并具有私有资源所需的访问权限。群晖建议使用固定目录：

```bash
mkdir -p /volume1/docker/cageledger
cd /volume1/docker/cageledger
git clone https://git.cellnucle.us/hugo/cageledger.git .
cp .env.example .env
```

编辑 `.env`，设置初始管理员用户名、至少 12 位的随机 `CAGELEDGER_ADMIN_PASSWORD`，以及准备部署的 `CAGELEDGER_IMAGE_TAG`。以下命令中的 `X.Y.Z` 均需替换为已发布版本。

生产首次创建管理员时拒绝空用户名和弱口令；已有数据库存在账号时，修改初始化环境变量不会重置密码或改变权限。`.env` 含凭据，应限制读取权限。完整配置见[环境变量](/operations/environment)，账号管理见[账号与权限](/operations/accounts-and-permissions)。

### 2. 拉取并启动

```bash
CAGELEDGER_IMAGE_TAG=X.Y.Z docker compose pull
CAGELEDGER_IMAGE_TAG=X.Y.Z docker compose up -d
```

镜像地址为 `ddns.cellnucle.us:3333/hugo/cageledger:X.Y.Z`。`docker-compose.yml` 使用 Packages 镜像；`docker-compose.offline.yml` 用于从已有源码构建，构建依赖仍须通过网络或预备缓存取得。

Compose 将同级 `./data` 绑定到 `/app/data`。若部署目录为 `/volume1/docker/cageledger`，则数据落在 `/volume1/docker/cageledger/data`，重建容器会继续使用该挂载目录。

### 3. 验证部署结果

```bash
docker compose ps
curl http://127.0.0.1:5173/api/health
docker logs --tail 100 cageledger
```

在浏览器访问 `http://NAS地址:5173`，核对健康检查中的版本、登录、文档、房间授权和主要业务页面。涉及转换器的部署还应抽查一份 PDF 和一份历史 Word 预览。健康检查成功只证明服务可响应，不能代替业务验证。

## 确认数据实际写在哪里

`server_app/config.py` 根据环境变量确定数据根和数据库路径。备份前核对实际服务配置，不能仅凭目录名判断。

| 配置                          | 生效规则                                                          |
| ----------------------------- | ----------------------------------------------------------------- |
| 都未设置                      | 数据根为仓库 `data/`，数据库为 `data/database/cageledger.sqlite`  |
| 仅设置 `CAGELEDGER_DATA_ROOT` | 数据库为该根目录下的 `database/cageledger.sqlite`                 |
| 设置 `CAGELEDGER_DB`          | 使用指定数据库；未另设数据根时，以该文件父目录为数据根            |
| 同时设置两者                  | 数据库与数据根分别使用显式值，可能位于不同目录                    |
| 使用当前镜像默认值            | `CAGELEDGER_DB=/app/data/cageledger.sqlite`，数据根为 `/app/data` |

其他资源通常位于数据根下：

```text
data/
├── database/               # 未显式指定 DB 时的数据库目录
├── indexes/iacuc/          # IACUC JSON 索引
├── files/                  # 巡检、接收、检疫、报销、反馈等文件
├── cache/pdf/              # 可再生成的 PDF 缓存
├── logs/                   # 持久化运行日志
├── backups/database/       # 数据库备份存放目录
├── inbox/iacuc/            # 自动导入投递目录
├── archive/iacuc/          # 已处理汇总表
└── failed/iacuc/           # 校验失败文件与报告
```

镜像默认的 `cageledger.sqlite` 及其 WAL／SHM 位于 `data/` 根部，不在上图的 `database/` 下。显式覆盖索引、附件、缓存或日志路径时，还要检查这些目录是否位于挂载范围内。备份范围与一致性要求见[备份与维护](/operations/backup-and-maintenance)。

从旧平铺目录迁移时，服务仅迁移未被对应环境变量覆盖的路径；首次迁移在 `data/rollback/` 保留回退副本，下次读取已完成标记时清理。目标已存在会拒绝迁移，不能通过删除某一份数据猜测解决。升级前仍应独立备份整个数据根及所有外置目录。

## 本地生产运行

先按[本地开发](/development/local-development#_1-准备运行时与依赖)安装 Node.js 22.x、Python 3.13 和依赖。在服务进程环境中设置初始管理员用户名与强口令后：

```bash
CAGELEDGER_ENV=production npm start
```

`npm start` 构建应用与文档，检查项目 Python 运行时，再启动服务。也可分步运行：

```bash
npm run build
node scripts/check_python_runtime.mjs
CAGELEDGER_ENV=production node scripts/run_python.mjs server.py
```

输出目录为 `web-dist/`。项目脚本使用 `.venv` 中的 Python 3.13，可通过 `CAGELEDGER_PYTHON_BIN` 显式覆盖。源码服务需要在进程环境中提供变量，不应假定 Compose 的 `.env` 会自动注入任意启动方式。

### 转换与文件处理依赖

| 功能                      | 必需组件                                   |
| ------------------------- | ------------------------------------------ |
| 历史 Excel 导入           | `openpyxl`                                 |
| 服务端 PDF 导出           | Python Playwright、Chromium、中文字体      |
| 检疫 Word 生成与预览      | `python-docx`；预览另需 LibreOffice Writer |
| 合格证 PDF 解析与页面渲染 | Poppler 的 `pdfinfo`、`pdftoppm`           |
| 图片识别预处理            | Pillow；原图不重写                         |

Python 生产依赖由 `requirements-runtime.txt` 冻结。Chromium 可由 Playwright 安装，或通过 `CAGELEDGER_CHROMIUM_BIN` 指定。服务预热并复用常驻浏览器；统计表后台预热与请求进度不改变最终导出校验要求。

生产镜像已包含这些组件，受管构建按 `runtime-image.lock.json` 复用不可变 ARM64 运行环境。依赖输入变化时由维护者显式刷新，普通部署不重新安装或改写锁定依赖，见[发布与交付](/development/release-and-delivery)。

## 离线交付方式

### 预构建源码包

默认云端 Release 不上传离线源码包。以下保留为本地归档和源码部署方式；Gitea 本地源码包构建另行配置：

```bash
npm run package:offline
```

得到 `dist/CageLedger-offline-X.Y.Z.tar.gz`，其中已包含 `web-dist/`。目标机解包后无需 Node.js，但仍需 Python 及上表中的系统组件：

```bash
tar -xzf CageLedger-offline-X.Y.Z.tar.gz
cd cageledger
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements-runtime.txt
CAGELEDGER_ENV=production .venv/bin/python server.py
```

启动前仍须配置初始管理员凭据。真正断网的目标机，应预备 Python 安装包、wheel 依赖和系统转换器；源码归档本身不提供完整运行环境。

### 完整 ARM64 镜像包

无法访问 Registry 的目标机可按需使用离线镜像。在可访问 Registry 的交付机器执行 `npm run package:offline:image`，默认拉取已发布 ARM64 镜像并导出镜像、加载说明和 SHA256 清单；显式 `--local` 可导出已核验的本地镜像：

```text
dist/CageLedger-image-X.Y.Z-arm64.tar.gz
dist/CageLedger-image-X.Y.Z-load.txt
dist/CageLedger-image-X.Y.Z-sha256.txt
```

目标机先按清单校验文件，再加载并固定版本：

```bash
docker load -i CageLedger-image-X.Y.Z-arm64.tar.gz
docker tag ddns.cellnucle.us:3333/hugo/cageledger:X.Y.Z-arm64 \
  ddns.cellnucle.us:3333/hugo/cageledger:X.Y.Z
CAGELEDGER_IMAGE_TAG=X.Y.Z docker compose up -d --pull never
```

上述方式复用已配置的 Compose 和 `.env`，保留账号、挂载与日志设置。镜像 tag 只包含版本，数字 build 仅用于系统展示。正式 Release 只有显式选择 `--offline-image` 才附带完整镜像，默认通过 Packages 拉取。

## 升级与回滚

### 升级前后

1. 确认目标版本、镜像平台与更新说明，记录当前镜像版本、配置和来源。
2. 按[备份流程](/operations/backup-and-maintenance#制作一致性备份)保存数据库、附件、索引、日志和部署配置。
3. 核对部署文件的来源。需要更新 Compose 时，从已确认的官方远端同步配置并保留本地 `.env`；不要盲目覆盖配置。
4. 固定新版本执行 `docker compose pull` 和 `docker compose up -d`。
5. 核对 `/api/health`、日志、管理员与房间管理员权限，再抽查笼卡、笼位、统计表、结算和单据跟踪。

服务启动自动执行幂等 schema 初始化与必要回填，旧库无需人工 SQL。正式环境使用明确版本，避免长期跟随 `latest`；升级期间出现数据或权限异常时，停止后续写入并保留现场。

### 回滚顺序

1. 停止写入，另存当前数据库与附件，保留升级后的故障证据。
2. 检查目标旧版是否兼容升级后的 schema 和数据。兼容时切回上一版镜像；有破坏性迁移时恢复同批升级前数据和配置。
3. 按[恢复与验证](/operations/backup-and-maintenance#恢复与验证)核对健康检查、账号权限、附件和关键业务链。

新增字段和索引通常可由旧版本忽略，但不能仅凭这一点承诺任意回滚。不可逆变更应由发布说明明确列出。

## 日常运行与群晖维护

正常诊断以挂载目录内的 `data/logs/runtime.jsonl` 为入口；Docker 控制台主要保留启动及文件写入失败时的应急日志。轮转、保留和读取方法见[备份与维护](/operations/backup-and-maintenance#运行日志与容量维护)，参数只在[环境变量](/operations/environment#运行日志)维护。

群晖可用 `scripts/sync_iacuc_summary_nas.sh once` 配合任务计划，或用 `watch` 常驻检测汇总表变化。脚本复制到 `inbox/iacuc/`，服务自动导入后归档；先核对源路径、目标目录及读写权限，详见[数据管理与 IACUC 索引](/operations/data-and-iacuc)。

数据目录可使用 Hyper Backup；支持 Btrfs 的存储可配合一致性快照，仍需定期恢复演练。外部访问使用受控反向代理和 HTTPS，证书下载、指纹核验及安装见 [HTTPS 与证书](/operations/https-and-certificate)。出现异常时按[故障排查](/operations/troubleshooting)收集证据。
