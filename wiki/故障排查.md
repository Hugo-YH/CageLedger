# 故障排查

本页面向系统管理员和开发维护者，从实际故障现象定位服务、请求和数据。先确认运行方式、版本、端口及数据目录，再记录最先出现的错误与请求 ID；处理后复现原操作验证结果。涉及生产数据的修复或恢复，应先保留现场并按既有授权执行。

## 先判断故障发生在哪一层

| 现象               | 首先检查                         | 继续定位                                                             |
| ------------------ | -------------------------------- | -------------------------------------------------------------------- |
| 整站无法访问       | 进程、端口、容器和反向代理       | [页面与连接](#页面打不开或空白)                                      |
| 页面正常，数据失败 | API 健康、失败请求状态和代理目标 | [API 请求](#页面可打开但-api-请求失败)                               |
| 登录或权限异常     | 当前数据库、已有账号和房间授权   | [账号与权限](#登录失败或权限异常)                                    |
| 数据或金额不符     | 业务来源、有效期、流程版本       | [IACUC](#iacuc-无法回填)、[结算](#结算金额异常)                      |
| 下载或转换失败     | 文件存在性、转换器、任务日志     | [文档转换与附件](#文档转换与附件异常)                                |
| 仅文档或更新异常   | 文档构建、Release 和配置         | [文档站](#文档站无法打开或内容过期)、[系统更新](#系统更新没有新版本) |

## 页面打不开或空白

开发模式由 Vite `5173`、Python API `5174`、VitePress `5175` 共同工作；生产与容器模式由 Python `5173` 提供同源页面和 API。先核对进程归属，避免误连旧服务。

```bash
lsof -i :5173
lsof -i :5174
lsof -i :5175
```

没有 `lsof` 时可使用系统的端口查看工具。开发模式依次检查：

```bash
curl http://127.0.0.1:5174/api/health
curl http://127.0.0.1:5173/api/health
curl -I http://127.0.0.1:5173/docs/
```

生产模式检查 `http://127.0.0.1:5173/api/health` 和 `web-dist/index.html`。容器环境查看 `docker compose ps`、`docker logs --tail 100 cageledger`；外部访问失败但本机正常时，继续检查端口映射、反向代理和 [HTTPS 证书](/operations/https-and-certificate)。

若服务可响应而页面空白，查看浏览器控制台第一条 JavaScript 错误及 Network 中首个失败资源。保存证据后，可使用工作区「刷新」重载本地 UI 状态；持续失败时核对前端资源与后端版本是否一致。

## 页面可打开但 API 请求失败

1. 直接访问 API 的 `/api/health`。开发环境默认 `5174`；无响应时先查看 Python 启动错误。
2. API 直连正常而 Vite 代理失败时，核对 `CAGELEDGER_API_ORIGIN` 与 Vite 终端代理错误。
3. 查看失败请求的状态码、响应和请求 ID。`401` 先核对会话，`403` 核对角色、房间及资源归属，`503` 结合并发或任务排队日志判断。
4. 核对访问协议、代理和 Cookie 配置；需要跨源时按[环境变量](/operations/environment)配置允许源，不随意开放所有来源。

修复后，从原页面重做同一操作，确认成功响应、界面刷新以及写入审计相符。

## 登录失败或权限异常

先确认连接的是预期数据库。源码默认 `data/database/cageledger.sqlite`，镜像显式使用 `/app/data/cageledger.sqlite`；路径被替换或挂载缺失会表现为账号、数据一并变化。

生产首次创建管理员需要配置非空用户名和至少 12 位的随机密码；已有账号不会被初始化环境变量重置。不要通过更换数据库尝试找回账号。登录成功但无法操作时，核对[账号与权限](/operations/accounts-and-permissions)中的角色、设施和房间授权，同时检查后端拒绝结果，不能只看菜单是否显示。

## IACUC 无法回填

1. 核对汇总表含 `动物伦理编号`、`动物实验名称`、`项目负责人`、`实验负责人`，编号与业务输入一致。
2. 在数据管理中检查上传／导入结果，抽查项目名称、负责人、来源和有效期。
3. 使用自动导入时，核对源文件、`inbox/iacuc/`、扫描配置及归档结果，查看导入失败日志。
4. 若兼容 JSON 索引写入告警，先确认 SQLite 是否已提交；数据库仍是系统查询来源，不通过覆盖 JSON 回退业务数据。

导入与派生字段规则见[数据管理与 IACUC 索引](/operations/data-and-iacuc)。处理后分别在数量统计表和笼位录入中核对回填。

## 结算金额异常

按来源到结果逐层检查：

1. 确认费用类型与来源。当前正式饲养费来自数量统计表，技术服务费有独立明细和账单。
2. 核对 IACUC、项目负责人、个人身份、计费月份及入驻／结束日期。
3. 核对转入转出、同日多类型和跨房间记录，确认镜像数据完整。
4. 核对 IACUC 有效期、PI 总额度、优先减免配置及逐日分配。
5. 核对同月候选与流程是否基于预期版本生成，再检查历史账单与导出。

不要直接改库平账。保存异常月份、来源和预期计算依据，沿[饲养费核算](/guide/billing)及[结算与报销](/guide/settlement-and-reimbursement)复核。报销登记和锁定归档是不同状态；旧「核销中心」不是当前工作区入口，见[兼容边界](/development/current-baseline)。

## 文档转换与附件异常

先区分原件下载失败、预览转换失败和 PDF 任务失败，保留原操作的请求 ID。

- 原件失败：核对账号权限、同批附件是否存在、外置路径与挂载是否一致。恢复后的缺失问题按[备份与维护](/operations/backup-and-maintenance)验证。
- PDF 失败：核对 Chromium、中文字体、浏览器启动与任务排队日志，确认输出版本和缓存来源。
- Word 失败：核对 `python-docx` 与 LibreOffice Writer；抽查同一份原始 Word 和预览接口。
- 合格证解析失败：核对 Poppler、文件类型与上传／识别阶段日志，再判断是否进入 AI 请求。

依赖清单见[部署与运行](/operations/deployment#转换与文件处理依赖)。不要仅增加超时或不断重试；先处理具体失败阶段，再验证一次同样输入。

## React 页面局部布局异常

确认当前版本和实际生产入口，再检查受影响组件、浏览器控制台与 computed style。依赖安装不一致时用 `npm ci` 恢复锁文件依赖；组件应接入项目 UI 适配层，样式查 `style-ownership.json` 的唯一来源。

大笼位图重点检查 TanStack Virtual 的行高估算、绝对定位和容器宽度；弹窗检查 Portal 作用域、视口定位和滚动所有者。按[测试与质量](/development/testing-and-quality)选择目标页面和相关用例，共享布局变化再扩大范围，避免每个局部问题都运行全量检查。

## 系统更新没有新版本

核对 Gitea 是否已发表 Release、当前版本是否已是最新、`CAGELEDGER_UPDATE_CHECK_ENABLED` 是否启用，以及私有仓库凭据是否可访问目标仓库。Git 提交、Packages 镜像和开发草稿都不等同正式 Release，流程见[发布与交付](/development/release-and-delivery)。

## 文档站无法打开或内容过期

开发环境确认 `5175` 的 VitePress 进程和应用 `/docs/` 代理；生产环境确认镜像中 `web-dist/docs/index.html` 与目标源码版本对应。导航或构建问题可运行 `npm run check:docs`；该命令构建文档，不验证业务功能。

文档源是 `wiki/`，Gitea Wiki 是迁移入口。云端交付不依赖 Mac 完成上传；若旧链接仍指向 Gitea Wiki，应从当前应用 `/docs/` 重新访问并核对发布版本。

## SQLite WAL 文件没看到

`-wal` 与 `-shm` 是 WAL 模式的运行时伴随文件，checkpoint 或连接正常关闭后可能消失。其缺席本身不是丢数据的证据；先确认主库路径及健康检查。运行中不能只复制主库，也不手工删除伴随文件，见[一致性备份](/operations/backup-and-maintenance#制作一致性备份)。

## 按日志关联一次请求

以 `data/logs/runtime.jsonl` 的请求 ID 关联 HTTP、后台任务和阶段耗时；重复错误一分钟限频，`suppressedCount` 表示期间额外次数。常用事件／操作如下：

| 问题             | 日志线索                                                                                     | 判读要点                                                    |
| ---------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| SQLite 锁        | `database_lock_error`                                                                        | 核对线程、操作及调用位置，不只看最后一次请求                |
| 待接收与接收读取 | `intake_list`、`reception_read`                                                              | 分清数量统计、分页、项目投影和原件读取                      |
| 合格证上传／识别 | `reception_certificate_upload`、`reception_certificate_recognition`                          | 用 `stage`、`durationMs` 区分查重、解析、渲染、预处理及保存 |
| AI 请求          | `ai_request_completed`、`ai_request_failed`                                                  | 按同一请求 ID 关联，不重复累计阶段耗时                      |
| 反馈同步         | `feedback_remote_sync_failed`、`feedback_remote_sync_recovered`、`feedback_worker_recovered` | 保留远端关联，先查失败阶段和恢复情况                        |
| 日志不可写       | `runtime_log_unavailable`                                                                    | 查磁盘空间、权限与挂载，修复后重启                          |

阶段耗时不含客户端上传前的传输时间。反馈无变化的正常轮询不记录成功事件，不能由缺少成功日志推断任务未运行。日志不记录附件正文或令牌，提交问题时也应只提供必要的脱敏证据。

保留时间、轮转及 Docker 应急日志边界见[备份与维护](/operations/backup-and-maintenance#运行日志与容量维护)。仍无法定位时，通过[帮助与反馈](/guide/feedback)提供版本、现象、复现步骤和请求 ID。
