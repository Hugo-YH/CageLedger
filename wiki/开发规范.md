# 开发规范

本页面向代码与文档维护者，按一次修改的顺序说明如何对齐基线、选择实现边界、验证并交付。具体模块与测试规则链接到唯一契约，避免在多页维护不同要求；代理另从仓库 `AGENTS.md` 进入。

## 1. 对齐源码与任务范围

开始前核对现有改动、当前分支、远端和 `package.json`，fetch 后比较上游，保留其他人的工作。常规修复和小功能在同步后的 `main` 完成，下一大版本使用 `beta`，预发布整合使用 `rc`，不为常规任务创建临时开发分支。

云端官方上游使用独立 `gitea` remote，地址为 `https://git.cellnucle.us/hugo/cageledger.git`；平台导入的 GitHub `origin` 保留。同步、凭据和分支分工见仓库 `docs/contracts/cloud-development.md` 与 `branching.md`，不能直接套用旧 Mac 文档的 `origin/main`。

环境要求与安装步骤见[本地开发](/development/local-development)。当前功能先对照[当前版本与兼容边界](/development/current-baseline)，再追踪实际入口；孤立组件测试和兼容导出不能证明当前菜单可达。

## 2. 沿现有边界实现

| 修改对象   | 应遵守的边界                                                                    | 详细规则                                                                 |
| ---------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 页面与请求 | typed hooks 访问服务端；Query 管业务数据，reducer 管显示偏好，局部 state 管草稿 | `frontend-state.md`、`api-contracts.md`                                  |
| 写入与 SQL | handler 管鉴权和响应，service 管校验、事务、审计和失效，repository 管数据访问   | `module-boundaries.md`、`write-safety.md`                                |
| UI 与反馈  | 复用 Ant Design 及项目适配层；确认、通知、结果与任务进度按用途呈现              | `ui-component-standard.md`、`ui-interaction-system.md`、`ui-feedback.md` |
| 主题与样式 | 使用唯一主题源和已登记样式归属，不在导入入口追加业务规则                        | `antd-design-language.md`、`ui-color-system.md`、`style-ownership.md`    |
| 查询与性能 | 分页、稳定排序、结构化热点列；按受影响范围刷新缓存                              | `shared-performance.md`                                                  |

表中的契约均位于仓库 `docs/contracts/`。新增后端业务进入 `server_app/domains/`；已有兼容层、旧字段与 payload 在迁移方案明确前继续保留。公共组件不反向依赖领域页面，纯业务函数不依赖 React、DOM 或网络。

## 3. 保持业务与数据语义

- IACUC 贯穿笼卡、占用、数量统计表和结算；Animal Record ID 是笼卡实例的持久唯一标识。
- `项目来源` 决定财务字段 `funding`。「已取材」与「设为空」保持独立语义。
- 当前正式饲养费来自数量统计表；笼位管理继续在用，隐藏的笼位图计费入口单独按发布状态维护。
- 转入转出同步目标伦理、镜像记录与结算；PI 减免同时考虑总额度、IACUC 有效期、优先设置和逐日分配。
- 当前报销登记与补录在单据跟踪完成，登记和锁定归档分别表达；旧台账、应收与核销 API 保留权限、资金归属和审计兼容。
- 权限变化同时核对前端入口和后端校验，设施写权限按授权房间控制；跨房间数量录入、结算导出与发起流程按现行授权执行。

不直接修改 SQLite、WAL、运行时 JSON，也不手工编辑 `data/`、`web-dist/`、`dist/`、`node_modules/`。调试与测试使用明确隔离的数据，不能仅凭 localhost 判断数据可丢弃。schema 迁移保持幂等和旧库回填。

## 4. 验证并交付可复核结果

按[测试与质量](/development/testing-and-quality)从 diff 选择明确目标，矩阵只维护在 `docs/contracts/testing-strategy.md`。高风险写入核对前端、API、SQLite 和审计；结算汇总同时检查 `src/react/print/settlement.ts` 与 `server_app/pdf/documents.py`，包括多页汇总。

相关改动完成后统一验证，已通过且未受影响的结果可复用。日常提交、推送不自动升级为完整 `check`、`verify:full`、构建或打包。最终执行 `git diff --check`，交付时说明改动、验证范围、未验证项与实际限制。

开发与浏览器服务通过受管启动器正常退出，核对本次子进程、浏览器和临时目录的清理；不按进程名批量清理。运行与收尾细节见[本地开发](/development/local-development#_3-修改、验证与退出)及测试策略。

## 5. 同步对应文档

用户操作、配置、权限和部署变化更新 `wiki/`；模块、状态、API 和 UI 约束更新 `docs/contracts/`。文档源按 `documentation-system.md` 管理，历史资料保留在 `docs/archives/`，不恢复为当前任务或授权。

`wiki/API接口清单.md` 由 API inventory 生成；系统内更新记录来自 `wiki/更新日志.md`，运行 `npm run release:notes:sync` 同步，不手工改生成文件。普通文档整理无需升级版本。

## 版本与正式交付

版本唯一源是 `package.json`，展示格式为 `a.b.c（Build N）`。`a` 表示重大／代际版本，`b` 表示功能更新，`c` 表示补丁；`-betaN`、`-rcN` 分别用于内测和候选，正式版本去掉后缀。build 为逐次递增的数字，不进入软件包 tag；Git 标签为 `v<version>`，镜像标签为 `<version>`。

准备新版本时使用 `scripts/set_version.mjs` 同步前端、HTML、更新日志与部署说明。正式交付先完成最终代码验证、提交推送、ARM64 构建与冒烟、附注标签和 Packages 核验，再运行 `npm run release:cloud -- --publish`。该命令只校验已备好的发布输入并发表 Release，不自动准备前述步骤。

生产运行环境由 `runtime-image.lock.json` 与 `requirements-runtime.txt` 固定，普通构建复用依赖层；依赖输入变化时显式执行 `npm run runtime:refresh` 并提交新锁，不移动业务版本或 latest。

日常验证后提交推送遵守当前工作约定；Packages、Release、latest 和生产部署分别按授权执行。完整交付、续传和 Mac 手动备用边界见[发布与交付](/development/release-and-delivery)，代理指令维护规则见仓库 `docs/contracts/agent-instructions.md`。
