# 备份与维护

本页面向管理员和运维人员，说明如何取得同批数据备份、在隔离目录演练恢复，以及在实际恢复后核对业务结果。先按[部署与运行](/operations/deployment#确认数据实际写在哪里)确认数据库、附件和外置路径；完成备份应得到可追溯的版本、配置、数据与校验记录。

## 备份范围与频率

| 对象           | 必须保留的内容                                                           | 建议时机                     |
| -------------- | ------------------------------------------------------------------------ | ---------------------------- |
| SQLite         | 实际 `CAGELEDGER_DB` 指向的数据库及一致性所需伴随文件                    | 每日、升级前、重要批量操作前 |
| 业务文件       | 完整 `files/`，包括检疫各版 Word、原始资料、报销附件、反馈截图与巡检文件 | 与数据库同批                 |
| 索引与导入资料 | `indexes/`、`inbox/`、`archive/`、`failed/` 及外置索引路径               | 与数据目录共同备份           |
| 部署配置       | `.env` 或服务环境配置、Compose、镜像版本与来源记录                       | 每周、每次变更和升级前       |
| 诊断与交付记录 | `logs/`、导出的结算文件、备份校验清单                                    | 升级前、故障时、每次结算后   |

推荐以完整部署配置和数据根为备份单元，再补充挂载目录以外的显式覆盖路径。`cache/pdf/` 可再生成，不能代替原始附件或历史账单。备份包含账号、业务及凭据，应保存在受限位置，不提交 Git。

## 制作一致性备份

<DocFigure src="/diagrams/backup-restore.svg" kind="diagram" alt="停止写入后取得同批数据库与附件，经过校验、隔离演练再进入恢复验收" caption="数据库与附件应为同一批次；隔离演练通过后，生产切换仍需独立执行和验证。" />

1. 记录应用版本、build、镜像 tag／摘要、实际数据库路径、数据根及所有外置目录。
2. 停服并确认写入结束后，复制完整数据目录与配置；也可使用同时覆盖数据库、附件及相关卷的一致性快照。
3. 生成文件清单或校验摘要，将备份批次与版本、时间、配置对应保存。
4. 重新启动原服务并核对健康检查；在独立位置执行下方恢复演练。

不要在服务持续写入时单独复制主 SQLite 文件。WAL 模式下，尚未合并的已提交数据可能位于 `-wal` 中；运行中的数据库应使用 SQLite 备份 API 等一致性机制，且仍需协调同批附件。<sup>[1](#参考资料)</sup> 停服后若伴随文件仍存在，保留原位副本，不通过手工删除 WAL 或 journal「修复」备份。

源码默认数据库为 `data/database/cageledger.sqlite`；当前镜像显式配置为 `/app/data/cageledger.sqlite`，映射到宿主机通常是 `data/cageledger.sqlite`。恢复演练示例中的路径必须按实际备份调整。

## 在隔离目录演练恢复

代码目录中的 `verify:restore` 会生成带清单的备份包，恢复到新目录，再核对业务记录、原审计、历史账单、核算结果和本地附件下载。它不切换生产环境。

```bash
npm run verify:restore -- \
  --database /absolute/offline-backup/database/cageledger.sqlite \
  --files /absolute/offline-backup/files \
  --output /absolute/new-private-restore-drill
```

### 输入条件

- 数据库与附件来自同批离线备份或一致性快照，不指向仍在写入的生产目录。
- 非空 WAL／journal 会被拒绝，工具不操作原库合并写入。
- 即使确实没有附件，也要显式提供空的附件目录。
- 输出是仓库外尚不存在的新目录，不覆盖旧证据，不与原始输入重叠。

### 判读结果

完成后查看 `report.md` 和 `report.json`。缺失附件、摘要差异、下载失败、原记录丢失、两份业务结果不同或阶段未完成均不能通过。已有历史业务问题可作为警告保留，不自动改业务记录。

默认检查 3 份代表性账单 PDF，全部历史账单快照、HTML 与 Excel 均会核对；需要全部 PDF 时增加 `--pdf-samples all`。`--timeout` 默认每份独立库 900 秒，可按备份规模明确调整。历史 Word 预览需要 LibreOffice 环境。

演练隔离远端凭据，Gitea 附件标记为远端未验证；本地缓存存在不代表可以脱网恢复。部署配置、运行日志、外部服务、浏览器版式和生产切换仍需单独验证。详细输入约束、退出码和覆盖范围见仓库 `docs/contracts/backup-restore-drill.md`。

## 恢复与验证

实际恢复前，先停止目标服务写入，另存当前数据库、附件与配置，再选定与备份相容的应用版本。将同批数据恢复到目标配置指定的位置，核对权限与挂载后启动，避免旧库和新附件混用。

| 验证层次   | 核对结果                                                   |
| ---------- | ---------------------------------------------------------- |
| 服务与账号 | `/api/health` 的版本正确；管理员和房间管理员登录、授权正常 |
| 基础业务   | IACUC 回填、首页、笼卡、笼位和数量统计表可读取             |
| 结算与流程 | 历史账单、核算结果、单据跟踪状态和审计可追溯               |
| 附件       | 检疫原始资料与旧版 Word、报销附件、巡检图片可下载／预览    |
| 反馈       | 截图、补充、工单编号、遇到人数及远端关联仍完整             |
| 外部集成   | Gitea、自动导入、更新检查及部署侧任务按配置恢复            |

反馈数据库中的原请求标识、目标仓库身份和同步任务必须保留。服务重启会恢复未完成任务；建单结果不确定时先核对远端标识，禁止清空关联后重新建单。

应用回滚优先评估上一版镜像对现有数据的兼容性；涉及破坏性迁移时，使用同批升级前数据和配置。完整顺序见[升级与回滚](/operations/deployment#升级与回滚)。

## 运行日志与容量维护

在部署目录读取日志：

```bash
tail -n 100 data/logs/runtime.jsonl
docker logs --timestamps --tail 100 cageledger
```

正常运行以持久化 `runtime.jsonl` 为诊断来源，Docker 控制台主要保存启动提示和文件写入失败后的应急记录。结构化日志包含 UTC 时间、版本、线程、请求 ID、结果与脱敏代码位置，不记录原始异常消息、SQL 参数、附件内容或外部令牌。业务审计保存在数据库，独立于运行日志。

| 行为     | 当前默认规则                                                                      |
| -------- | --------------------------------------------------------------------------------- |
| 分段     | 北京时间跨日或单份达到 10 MiB 时原子改名；同日重启继续追加                        |
| 文件名   | `runtime.YYYY-MM-DD.HHMMSS.PID.<12hex>.jsonl`；正文时间保持 UTC                   |
| 保留上限 | 最长 90 天、总容量 1 GiB、含当前文件最多 365 份，先达到任一限制即清理最旧受管归档 |
| 旧文件   | `runtime.jsonl.N` 保留原文并纳入清理；归档不压缩                                  |
| 降级     | 文件写入失败时控制台记录 `runtime_log_unavailable`，修复空间或权限后重启          |

90 天是保留上限，不能保证至少保存 90 天；后台清理期间容量可暂时超限。既有 `.env` 若仍设置 `CAGELEDGER_LOG_FILE_COUNT=5`，总份数仍为 5，需要按实际保留目标调整。轮转、容量和目录参数统一见[环境变量](/operations/environment#运行日志)。

两个 Compose 文件为应急控制台日志配置 `local` 驱动、10 MiB × 5 份轮转、非阻塞投递和 1 MB 缓冲。应急流量超出缓冲时可能丢弃，跨容器排查仍应保存整个持久化 `logs/`。归档或清理失败保留可恢复文件并告警，不改写业务审计。

日常维护检查磁盘剩余空间、备份批次、日志保留和最近一次演练结果。群晖可用 Hyper Backup，支持 Btrfs 的设备可配合快照；快照可用性和实际恢复仍需演练验证。故障事件的定位方法见[故障排查](/operations/troubleshooting#按日志关联一次请求)。
