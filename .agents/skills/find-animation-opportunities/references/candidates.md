# 动效机会参考

根据实际页面判断候选是否有帮助；无需按固定顺序答题、打分或凑数量。项目 Token 与无障碍要求优先。

## 选择依据

- 用途：操作反馈、状态变化或空间关系是否不够清楚？静态文字、颜色或布局能否更直接地解决？
- 频率：高频列表、筛选和键盘操作优先即时响应。低频场景也不必自动增加动画。
- 响应：过渡是否延迟输入、遮挡内容或造成位移？使用项目现有时长档位，按实际组件调整。
- 连续性：快速重复或反向操作是否自然？减少动态效果后是否仍能理解和使用？

## 候选场景

| 观察到的问题             | 可考虑的方式                         | 保留的边界                             |
| ------------------------ | ------------------------------------ | -------------------------------------- |
| 点击后不知是否开始处理   | 按钮 loading、明确状态或轻微按压反馈 | 不重复提交，不靠动画代替真实进度       |
| 内容切换造成明显跳动     | 稳定容器、局部占位或短过渡           | 有数据时保留内容，不反复卸载输入和浮层 |
| 弹窗或抽屉出现位置难理解 | 沿用组件的过渡与定位                 | 键盘和触屏可达，减少动态效果可关闭动画 |
| 拖动后突跳或反向不连续   | 当前值衔接、速度连续或适当阻尼       | 仅在产品存在相应手势时采用             |
| 成功或错误反馈难发现     | 站内提示、字段说明或状态强调         | 不依赖移动或闪烁表达状态               |

已有反馈足够、纯淡入或无动画均可接受。保持现有危险操作确认流程，不因为动效建议改成长按确认。缺少缩放、错峰或弹簧本身不是问题。

报告可定位的候选、用途、建议行为及验证方式，标明实测与假设。只有用户要求实现时才修改源码。
