# 业务写入安全约束

## 写入意图

- 创建操作使用 `POST`，客户端为每次新草稿生成新的 ID。
- 编辑操作仅从已保存记录进入，使用 `PUT /{id}`。
- 连续录入页面在创建成功后立即回到新草稿状态。
- 状态推进使用专用动作接口，服务端在单个事务内校验当前状态。

## 并发版本

新增写入接口遵循以下规则；现有入口的兼容策略和实现限制见下方表格。

- 已保存的业务记录通过 `updatedAt` 表示服务端版本。
- 前端更新请求携带 `expectedUpdatedAt`。
- 服务端在事务内比对当前版本；版本变化返回 `409` 和“刷新后重新编辑”提示。
- 服务端负责写入新的 `updatedAt`，客户端不生成记录版本。

### 当前兼容边界

以下表格描述实际支持的策略。通用并发版本规则是新增接口的目标，不能据此断言所有历史写入口均为必填版本或已实现统一的原子CAS。

| 策略               | 当前入口                                                                                                         | 缺省版本                            | 版本匹配与事务边界                                                                                                                                                                                    |
| ------------------ | ---------------------------------------------------------------------------------------------------------------- | ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 兼容可选版本       | 已有ID的数量统计表保存、批次／占用／进驻任务编辑、原通用实体版本入口、账号、负责人配置、原报销台账、巡检目录草稿 | 继续放行，不自动收紧                | HTTP写入口在读取待修改记录前取得SQLite写锁，版本校验、保存和原审计在同一事务；数量表写入直接读取数据库，不以详情缓存作为版本依据。`require_current_version` 保留原字符串清理和比较，提供过期版本时409 |
| 必填精确版本       | 技术服务明细编辑／删除；检疫编辑、删除、更正、复检及附件元数据等现有版本入口                                     | 409                                 | `require_exact_version` 不做字符串强制转换或去空白；领域入口保留原写锁、状态和权限校验顺序，原错误文案不变                                                                                            |
| 显示配置版本       | 系统功能入口显示配置                                                                                             | 必填，首次为null                    | 独立配置表在同一写事务内重读版本、保存入口开关及审计；过期409，无实际变化不重复写入，不修改业务表                                                                                                     |
| 来源版本集合       | 技术服务发起结算                                                                                                 | 拒绝缺少或不匹配的 `sourceVersions` | 原事务内重读全部源明细并核对版本后保存账单快照及审计                                                                                                                                                  |
| 状态动作／资金约束 | 工作流推进、登记、撤销、锁定及解锁；报销和核销操作                                                               | 不统一添加 `expectedUpdatedAt`      | 保留事务内状态、经手账号、锁定授权、已确认核销及原子余额上限校验                                                                                                                                      |
| 旧删除／全量入口   | 原数量统计表、批次和通用实体删除；`PUT /api/state`                                                               | 沿用原入口                          | 不套用技术服务／检疫的必填版本规则；原关联清理、权限及资金保护保持不变                                                                                                                                |

`begin_write(conn)` 在尚无事务时执行 `BEGIN IMMEDIATE`，由原调用方继续负责提交与回滚；嵌套领域服务复用调用方已经取得写锁的事务，不自行提交外层事务。它不改变版本参数的可选／必填口径，也不为旧接口新增版本要求。基础设施原来没有执行版本比对的入口仍按原规则处理，只将引用校验和保存置于同一写事务。

通用实体更新从同一连接读取最新聚合、检查版本、修改、保存并记录原审计，避免读旧聚合后经另一连接覆盖并发修改。`PUT /api/state` 的服务端读取、权限、差异审计与保存也处于同一写事务；它仍是原来的全量替换接口，没有新增全局版本字段，不能据此承诺拒绝旧客户端提交的过期全量内容。未提供版本的旧编辑请求仍可能按原规则覆盖同一条记录，不启用自动写入重试。

现有结算流程附件上传入口只要求登录、流程存在及文件校验，未按经手人或锁定状态限制。此次盘点在清单中明确记录，未将它改成新的权限口径；不能把工作流推进的状态／经手人保护直接等同于所有附件操作的保护。

### 幂等与审计核对

| 入口                           | 现有重放规则                                                                   | 事务和审计                                                                                                         |
| ------------------------------ | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| 技术服务创建                   | 同账号、草稿ID和创建签名复用；不同输入或已删除ID拒绝                           | 原写事务中校验、保存并审计，重放不重复审计                                                                         |
| 反馈创建、补充、附件及工单导入 | `requestId` 绑定账号及内容；不同内容拒绝，逐项导入结果保留                     | 原本地事务及任务去重保持；网络请求不放在数据库写事务中                                                             |
| 检疫出具与批次完成             | 出具重试复用已有版本，重复完成复用已有完成记录                                 | 原版本与关联报告校验、失败保留草稿、审计规则不变                                                                   |
| 批次重复提醒                   | 新页面启用可选查重，重复确认绑定本次草稿与完整匹配集合；旧客户端仍允许重复编号 | 未确认不写入；确认后在同一写事务内复核并追加 `intake_batch.duplicate_confirmed` 审计；不改变旧ID唯一及编辑版本规则 |
| 原数量统计表创建／保存         | 相同ID可能进入编辑并追加审计，不视作通用幂等重放                               | 原统计表、转移镜像和审计事务保持；允许同月份／伦理／房间多张表                                                     |
| 其他创建和动作                 | 实体唯一ID、单号或状态校验不等于统一请求幂等协议                               | 逐接口记录现有行为，不额外启用写入重试                                                                             |

月报与欠缴 Excel 导入先完成工作簿边界和金额校验，明确非法输入不写业务记录或审计；通过后在首次读取既有台账前取得 `begin_write` 写锁，避免覆盖并发登记的已缴金额。原有同月同负责人更新、已有ID与手工登记保留规则继续生效，不新增必填版本或统一幂等协议。校验和写入失败由原HTTP连接事务回滚，只有成功提交后才失效读缓存。

完整的“方法＋路径”、鉴权、入参／响应摘要、重放、事务及审计副作用见 `docs/contracts/api-inventory.json`，生成的开发参考位于 `wiki/API接口清单.md`。特别保留应收查询触发来源同步、反馈详情排队刷新以及远端附件缓存／可见性复核等既有GET副作用；本轮不把它们改成不同的业务写入时机。

## 审计与恢复

预约原图暂存按账号隔离，失效引用在业务写入之前返回410；仅此错误允许页面重新上传再重试一次。版本、权限和重复确认错误不自动重试。图片的排他创建与fsync在SQLite写锁前完成，事务内继续权限、版本、查重及来源关联校验；失败只清理本次拥有的文件，成功后的未使用副本也清理，不覆盖原件。暂存ID不进入业务payload或审计；备份继续使用成功保存的独立原件。

接收合格证原件按批次与SHA去重，识别按账号/requestId复用已留档任务；新请求不得与未完成识别并行处理同附件。AI调用和PDF处理不占用写事务，失败保留原件及任务状态。独立接收登记确认同时精确校验批次、登记和申请资料版本，并要求人工核对；账号/requestId/请求签名重放返回原结果，不重复审计。旧识别结果经当前版本下人工核对后可沿用，其原版本及字段来源继续留档；不改写预约、笼卡、占用、项目或计费记录。原件与预览均进入备份恢复引用核查。

- 关键写入继续记录操作者、时间、变更前后快照和业务实体 ID。
- 恢复脚本只通过业务写入服务创建新记录，恢复记录携带来源审计事件 ID。
- 恢复后的笼卡使用新的批次 ID 和二维码，避免与历史记录冲突。

预约文字合并复用批次PUT，但仅该显式分支要求 `expectedUpdatedAt` 与只读预览的 `confirmationToken`。预览不写库；保存取得写锁后按原图重算、复核完整编号匹配集合，保留原ID、原图和状态并原子写入原更新审计与 `intake_batch.recognition_merged`。普通批次编辑的可选版本与重复确认边界保持。多人匹配、关联冲突、无留档图片或已经接收的预约不提供合并。

### 接收编号兼容

`purchaseOrderNo` 与 `orderNo` 分别保存采购申请单号和完整订单编号，禁止将DC后缀丢弃后仅存C。共享标准化只对严格 `DC[0-9]{13}[0-9]{2}` 推导 `C[0-9]{13}`，唯一明确的C/DC关系冲突在写入前拒绝；其他格式不猜测。查重及合并令牌同时绑定采购单号、完整订单编号和批次号。不同编号集合间的自动补充合并保持保守，不能把同C下的不同DC订单静默覆盖；同一预约内显式登记多个DC订单则允许保存。

兼容升级在调用方写事务中增加非唯一订单查询列、回填标量与拆分历史混存的业务字段；原始文字、图片证据、批次ID、状态和业务版本保持保留，仅实际拆分追加 `intake_batch.identifiers_migrated` 系统审计。升级幂等，字段回填或审计失败一并回滚。旧记录原本缺失且未推导出有效值的编号字段保持缺失，不因查询列需要空字符串而补写到业务快照或审计 `before`；显式空值仍保留其存在性。旧实体编辑和全量状态请求省略 `orderNo` 时保留已保存值；显式清空仍按普通编辑处理，不新增版本要求或自动重试。

预约原文编号补填独立于上述格式兼容：启动时在同一写事务内执行一次，使用 `app_settings.intakeIdentifierBackfillV1` 留存执行结果。仅从保留原文中提取唯一、完整的 C13／DC15 编号补齐空白字段；全角字符只在识别副本中规范化，原文和图片依据保持。多个编号、C/DC 对应冲突、非空人工字段冲突及审计中明确清空的字段跳过，记录 `intake_batch.identifier_backfill_skipped`。实际补填记录 `intake_batch.identifiers_backfilled`，包含前后值、原文哈希与来源候选，并更新记录版本，使当前页面的过期编辑请求返回409。采购及订单查询投影、版本、审计和一次性标记原子提交，失败一起回滚；重复启动、后续新记录或人工清空不会重复补填。不修改笼卡、接收明细、状态、项目、计费或历史审计。

多编号使用可选 `identifiers` 集合保存同一预约的采购单、完整订单和需求批次，旧字符串继续作为顿号投影；它不表示笛卡尔积配对或数量分摊。新增 `intake_identifier_members` 成员投影及非唯一查找索引，按单个编号查重、筛选和检索；不同预约可复用成员，复用仍经原重复确认和审计流程。写入、编辑、删除同步维护成员，与原业务写事务同提交。兼容迁移只结构化已保存字段里的明确标准多编号，保留记录ID、数量、笼卡、接收及来源，更新版本并追加 `intake_batch.identifiers_grouped`；成员表、版本、审计失败一起回滚，重复升级不重复审计。旧客户端省略集合时从实际提交的字符串重建，显式清空不会被旧集合恢复；标准DC仍按原规则派生对应C。跨IACUC需求禁止放入同一新预约，金额、权限和计费口径不变。

### 接收批次局部事务

接收批次创建、编辑、删除、打印标记与接收动作在原 `BEGIN IMMEDIATE` 内读取目标批次、关联任务/占用及必要房间配置，复用原状态校验、权限与差异审计规则。完整业务快照不再作为单批次写入的前提；其他聚合接口保持原行为。普通编辑的可选版本、合并的必填精确版本、批量接收的版本集合、重复确认与各动作原授权顺序保持。

笼卡短码仍核对全局批次、任务和占用，只读取短码投影；当前批次及其关联任务的排除规则与原收集器一致。读取、校验、编号成员投影、关联任务写入和审计使用同一连接及事务；失败回滚业务及审计，本次新留档图片由原文件写会话清理。原批次ID、已有笼卡短码、原图字节、打印模板和计费数据不因此次职责整理而迁移或重建。

## 实验人员目录

人员目录独立存于 `researchers`，使用稳定人员ID与唯一规范通讯录账号；不创建登录账号，不以姓名或手机号合并，不改已有业务快照、身份减免与历史审计。升级只增加人员表、导入请求表和索引，空目录不自动导入本地文件；完整SQLite备份包含目录及审计。

上传预览只读，管理员确认时在 `BEGIN IMMEDIATE` 内读取当前目录版本，重新解析原文件并复核文件SHA与匹配集合版本构成的确认令牌。任一错误行阻止全部写入，空白可选字段不覆盖旧值，文件缺失人员不删除。按账号/requestId/文件与令牌签名复用确认结果；账号相同但内容不同的同次请求409，成功重试不新增审计。逐人前后快照、导入统计和幂等结果同事务提交，审计失败全部回滚。手工编辑要求精确 `expectedUpdatedAt`，可显式清空联系方式，冲突409且不自动重试。来源禁用状态不参与系统账号授权。

## 当前覆盖

覆盖程度按上方实际策略和接口清单区分。共享兼容版本与必填精确版本均有回归；涉及结算、权限和资金的现有领域回归继续保留。接口清单检查只验证元数据、引用和路由复核状态，不替代并发、权限、SQLite及审计的实际验证。
