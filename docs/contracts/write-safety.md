# 业务写入安全约束

## 写入意图

- 创建操作使用 `POST`，客户端为每次新草稿生成新的 ID。
- 编辑操作仅从已保存记录进入，使用 `PUT /{id}`。
- 连续录入页面在创建成功后立即回到新草稿状态。
- 状态推进使用专用动作接口，服务端在单个事务内校验当前状态。

## 并发版本

新增写入接口遵循以下规则；现有入口的兼容策略和实现限制见下方表格。

- 已保存的业务记录通过 `updatedAt` 表示服务端版本。
- 前端更新请求携带 `expectedUpdatedAt`。
- 服务端在事务内比对当前版本；版本变化返回 `409` 和“刷新后重新编辑”提示。
- 服务端负责写入新的 `updatedAt`，客户端不生成记录版本。

### 当前兼容边界

以下表格描述实际支持的策略。通用并发版本规则是新增接口的目标，不能据此断言所有历史写入口均为必填版本或已实现统一的原子CAS。

| 策略               | 当前入口                                                                                                         | 缺省版本                            | 版本匹配与事务边界                                                                                                                                                                                    |
| ------------------ | ---------------------------------------------------------------------------------------------------------------- | ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 兼容可选版本       | 已有ID的数量统计表保存、批次／占用／进驻任务编辑、原通用实体版本入口、账号、负责人配置、原报销台账、巡检目录草稿 | 继续放行，不自动收紧                | HTTP写入口在读取待修改记录前取得SQLite写锁，版本校验、保存和原审计在同一事务；数量表写入直接读取数据库，不以详情缓存作为版本依据。`require_current_version` 保留原字符串清理和比较，提供过期版本时409 |
| 必填精确版本       | 技术服务明细编辑／删除；检疫编辑、删除、更正、复检及附件元数据等现有版本入口                                     | 409                                 | `require_exact_version` 不做字符串强制转换或去空白；领域入口保留原写锁、状态和权限校验顺序，原错误文案不变                                                                                            |
| 显示配置版本       | 系统功能入口显示配置                                                                                             | 必填，首次为null                    | 独立配置表在同一写事务内重读版本、保存七项开关及审计；过期409，无实际变化不重复写入，不修改业务表                                                                                                     |
| 来源版本集合       | 技术服务发起结算                                                                                                 | 拒绝缺少或不匹配的 `sourceVersions` | 原事务内重读全部源明细并核对版本后保存账单快照及审计                                                                                                                                                  |
| 状态动作／资金约束 | 工作流推进、登记、撤销、锁定及解锁；报销和核销操作                                                               | 不统一添加 `expectedUpdatedAt`      | 保留事务内状态、经手账号、锁定授权、已确认核销及原子余额上限校验                                                                                                                                      |
| 旧删除／全量入口   | 原数量统计表、批次和通用实体删除；`PUT /api/state`                                                               | 沿用原入口                          | 不套用技术服务／检疫的必填版本规则；原关联清理、权限及资金保护保持不变                                                                                                                                |

`begin_write(conn)` 在尚无事务时执行 `BEGIN IMMEDIATE`，由原调用方继续负责提交与回滚；嵌套领域服务复用调用方已经取得写锁的事务，不自行提交外层事务。它不改变版本参数的可选／必填口径，也不为旧接口新增版本要求。基础设施原来没有执行版本比对的入口仍按原规则处理，只将引用校验和保存置于同一写事务。

通用实体更新从同一连接读取最新聚合、检查版本、修改、保存并记录原审计，避免读旧聚合后经另一连接覆盖并发修改。`PUT /api/state` 的服务端读取、权限、差异审计与保存也处于同一写事务；它仍是原来的全量替换接口，没有新增全局版本字段，不能据此承诺拒绝旧客户端提交的过期全量内容。未提供版本的旧编辑请求仍可能按原规则覆盖同一条记录，不启用自动写入重试。

现有结算流程附件上传入口只要求登录、流程存在及文件校验，未按经手人或锁定状态限制。此次盘点在清单中明确记录，未将它改成新的权限口径；不能把工作流推进的状态／经手人保护直接等同于所有附件操作的保护。

### 幂等与审计核对

| 入口                           | 现有重放规则                                               | 事务和审计                                                     |
| ------------------------------ | ---------------------------------------------------------- | -------------------------------------------------------------- |
| 技术服务创建                   | 同账号、草稿ID和创建签名复用；不同输入或已删除ID拒绝       | 原写事务中校验、保存并审计，重放不重复审计                     |
| 反馈创建、补充、附件及工单导入 | `requestId` 绑定账号及内容；不同内容拒绝，逐项导入结果保留 | 原本地事务及任务去重保持；网络请求不放在数据库写事务中         |
| 检疫出具与批次完成             | 出具重试复用已有版本，重复完成复用已有完成记录             | 原版本与关联报告校验、失败保留草稿、审计规则不变               |
| 原数量统计表创建／保存         | 相同ID可能进入编辑并追加审计，不视作通用幂等重放           | 原统计表、转移镜像和审计事务保持；允许同月份／伦理／房间多张表 |
| 其他创建和动作                 | 实体唯一ID、单号或状态校验不等于统一请求幂等协议           | 逐接口记录现有行为，不额外启用写入重试                         |

完整的“方法＋路径”、鉴权、入参／响应摘要、重放、事务及审计副作用见 `docs/contracts/api-inventory.json`，生成的开发参考位于 `wiki/API接口清单.md`。特别保留应收查询触发来源同步、反馈详情排队刷新以及远端附件缓存／可见性复核等既有GET副作用；本轮不把它们改成不同的业务写入时机。

## 审计与恢复

- 关键写入继续记录操作者、时间、变更前后快照和业务实体 ID。
- 恢复脚本只通过业务写入服务创建新记录，恢复记录携带来源审计事件 ID。
- 恢复后的笼卡使用新的批次 ID 和二维码，避免与历史记录冲突。

## 当前覆盖

覆盖程度按上方实际策略和接口清单区分。共享兼容版本与必填精确版本均有回归；涉及结算、权限和资金的现有领域回归继续保留。接口清单检查只验证元数据、引用和路由复核状态，不替代并发、权限、SQLite及审计的实际验证。
