# 通知与操作反馈契约

本契约统一 CageLedger 用户可见反馈的组件分类、触发时机、文案和开发边界，适用于工作台、登录、公开扫码及公共组件。新增反馈和存量迁移遵守本契约；业务权限、事务、审计及确认流程保持各自契约。

全系统操作反馈已接入下述公共入口；[全系统盘点与迁移记录](../analysis/ui-feedback-inventory-2026-11-02.md)保留迁移前用途、分类及落实情况。页面上的持久风险、字段校验、业务确认和状态展示仍按各自职责原位呈现。

## 三类组件的选择

先判断反馈的作用范围与后续操作，再判断成功、提示、警告或错误。严重程度不决定组件种类；`success Alert` 可能是持久业务结论，不能一律改为弹出成功通知。

| 类别                          | 回答的问题                                           | 适用内容                                                                                     | 展示及生命周期                                                           |
| ----------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Notification／通知提醒框（N） | 这次业务操作或后台任务有什么结果？                   | 保存、删除、登记、发起、撤回、上传、导出等结果；需要进度或后续入口的长任务                   | 桌面右上角；支持标题、说明、关闭与必要操作；任务用同一条通知更新         |
| Message／全局提示（M）        | 刚才的轻量交互是否生效？                             | 复制成功、选择已清空、达到选择上限、本地草稿调整、没有可执行内容、保存中暂不能离开           | 顶部居中短提示；简短、自动消失，不承载必须阅读或处理的资料               |
| Alert／警告提示（A）          | 当前页面或对象有什么需要持续关注、修复或重试的问题？ | 表单请求失败、版本冲突、来源不确定、旧数据、权限或配置阻塞、附件部分失败、识别差异、冻结限制 | 留在相关页面、表单、抽屉或对象旁；直到问题解决、范围改变，或允许用户关闭 |

判断顺序：

1. 有具体错误字段，使用 Ant `Form.Item` 的校验与帮助信息。
2. 需要用户授权、确认风险或作出流程决定，使用业务 `Modal`／`Popconfirm`。
3. 必须结合当前对象持续查看、修复或重试，使用 Alert。
4. 是服务器业务结果、异步文件操作或长任务，使用 Notification。
5. 其余即时、轻量且可自动消失的交互反馈，使用 Message。

例如保存失败后仍在编辑表单中重试，应在表单内显示 Alert；列表中无需编辑表单的独立删除请求失败可用 Notification。业务完成且弹窗关闭后，成功结果应由 Notification 展示。

## 不属于三类通知的内容

| 内容                                                                               | 保留的组件或行为                                                     |
| ---------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 必填、金额、数量、日期格式及逐行明细校验                                           | `Form.Item`、字段帮助、可定位错误汇总；不只弹出一个会消失的错误      |
| 删除、重复编号仍保存、实际接收日期、撤回、锁定、经费本差异、结算邮件与放弃草稿确认 | 业务 Modal／Popconfirm；通知不能代替确认，也不能代为同意             |
| 初载、分页、查询、按钮执行进度                                                     | Skeleton、Spin、`loading`、`ListRefreshStatus`；正常刷新不弹成功消息 |
| 空列表、公开扫码无匹配、页面无法加载                                               | Empty、Result、PageState 与原位恢复入口                              |
| 检疫完成、单据已锁定、IACUC 有效期、同步状态、健康状态                             | Tag、Badge、Tooltip、详情文字；需要持续说明时配 Alert                |
| 识别原件、字段差异、导入逐项结果、批量失败名单                                     | 业务表格、对照、Collapse 或详情；可有概要通知，明细仍可回查          |
| 更新日志公告、通知邮件正文                                                         | 原公告阅读／确认弹窗、邮件业务流程；名称含“通知”不代表 Notification  |
| 摄像头取景、扫码候选、当前选择指引                                                 | 设备状态或工作区指引；设备失败及恢复方法留原位                       |

浏览器文档卸载仍由现有 `beforeunload` 保护未保存内容；站内导航沿用未保存确认。服务器日志、审计事件和 HTTP 错误不是 UI 通知本身，不能逐条直接弹出。

## 呈现和严重程度

下面的时间、位置与折叠规则是项目约定，不是 Ant Design 默认值。

| 组件及情况                      | 约定                                                                        |
| ------------------------------- | --------------------------------------------------------------------------- |
| Notification 成功               | `success`，通常 3 秒自动关闭；标题给出完成动作，说明列对象或数量            |
| Notification 普通信息           | `info`，通常 5 秒；仅用于需要通知的业务结果或任务阶段                       |
| Notification 重要警告／部分成功 | `warning`，保留至手动关闭；提供现有失败详情或核对入口                       |
| Notification 失败               | `error`，保留至手动关闭；说明已知结果和下一步，不自动重放写操作             |
| Notification 运行中             | 持续显示，以相同 key 更新；完成后转成功、警告或失败，不另弹一串新通知       |
| Message                         | 通常 3 秒；可按语义使用 success／info／warning／error，同类重复触发复用 key |
| Alert                           | 按当前实际状态显示；成功、说明、警告、错误分别采用对应 Ant 语义类型         |

- Notification 桌面使用 `topRight`，手机使用顶部适配视口宽度；Message 使用顶部居中；通知堆叠的顶部位置为桌面 80 px、手机 96 px，为同时出现的轻提示留出空间。间距、颜色、字号、动画、层级和安全区由公共适配层、主题及[样式归属](style-ownership.md)统一管理，业务页不自行偏移或添加高 z-index。
- Notification 默认保留关闭按钮、鼠标悬停暂停计时，超过 3 条使用堆叠。堆叠与 `maxCount` 丢弃旧条目不同，不能因达到数量上限而无提示地丢失仍需处理的失败或任务。
- Notification 的成功与普通信息显式使用温和的 `role="status"`；需要立即介入的错误使用 `role="alert"`。其他组件沿用 Ant 的可访问行为，不向 Message 传入其类型不支持的属性；通知不抢焦点、不锁焦点，不以颜色作为唯一状态区分。
- `showProgress` 是自动关闭倒计时；任务完成比例由真实 `completed / total` 驱动的 Progress 展示。总量未知时显示阶段文字或不定进度，不编造百分比。
- 业务阻塞的 Alert 在问题未解决时保持可见；允许关闭的普通说明可由用户关闭。关闭提示只改变显示，不清空草稿、推进流程、确认风险或取消任务。

## 业务结果的表达

标题用“对象＋动作结果”，说明给出对象、范围、数量或恢复方法。成功信息不能仅靠图标，失败不能只写“操作失败”。

| 实际证据                             | 合适表达                                             | 不得推断的结果                                         |
| ------------------------------------ | ---------------------------------------------------- | ------------------------------------------------------ |
| 保存接口成功，记录已持久化           | “数量统计表已保存”                                   | 页面刚关闭、列表刚刷新就认为保存成功                   |
| 复制接口成功                         | Message：“负责人信息已复制”                          | 资料已发送或已通知对方                                 |
| 业务主体成功、部分附件失败           | “反馈已提交，2 张截图上传失败”；局部保留原文件及重试 | 报告全部失败，或仅显示“提交成功”后丢失附件问题         |
| 批量 8 条成功、2 条失败              | warning：“已完成 8 条，2 条未完成”；显示原失败明细   | 将整个批量标成纯 success，或因一条失败否认全部已完成项 |
| 后台同步请求已受理                   | “同步请求已发起”                                     | 未读取远端结果就声称“已同步至 Gitea”                   |
| PDF 任务 ready，已触发浏览器下载     | “PDF 已生成，下载已开始”                             | 已保存到用户磁盘、已打印或已签收                       |
| 浏览器打印窗口已打开／已标记打印     | “已打开打印窗口”／“已标记为已打印”                   | 实物打印完成                                           |
| 请求超时或结果同步失败，写入结果未知 | “结果暂未确认，请刷新核对后再操作”                   | 未核对就断言零写入、自动重提或显示操作成功             |
| 更新检查发现 Release                 | “发现新版本”，保留版本及来源                         | 已安装、已发布到生产或已部署                           |

本地移除尚未保存的目录条目、照片或表单行，使用 Message 表达“已从当前草稿移除，保存后生效”；只有服务器删除成功才能使用持久化删除成功通知。

## 公共入口与代码归属

Ant 容器在 `src/react/components/ui/AntdProvider.tsx`，统一配置桌面右上角／手机顶部、堆叠、宽高边界和主题。任务通知在 `src/react/components/TaskFeedback.tsx`／`src/react/components/TaskFeedbackContext.ts`，由 `src/main.tsx` 挂载；PDF 调用在 `src/react/features/billing/hooks/usePdfExport.ts`。

开发与维护遵守以下边界：

1. 公共反馈入口复用 `AntdProvider` 内的 `App.useApp()` 实例；优先扩展现有 TaskFeedback。统一管理 Notification／Message 的配置与调用，不另造业务域通知容器、事件总线或并行任务队列。
2. 新公共封装放在 `src/react/components/` 或其 hooks 适配层；领域状态及权限仍由业务组件和 typed hooks 持有。不要引入第二份 TanStack Query 业务缓存。
3. 不使用脱离 Context 的静态 `message.*`／`notification.*` 调用；统一入口保证主题、语言、移动端和减少动画配置生效。Alert 继续由当前上下文渲染。
4. 使用已安装版本支持的 API，Notification 使用 `title`、`description`、`actions`；不引入废弃的 `message` 标题字段或 `btn`，不为本次统一升级组件库。
5. 业务动作拥有其最终反馈。组件与 API hook 不同时弹同一结果；复合操作的内部保存、轮询、缓存失效不单独报成功。巡检提交先保存草稿时，只汇报用户选择的最终动作及实际部分结果。
6. 通知在操作完成回调中显式触发，不在 render、查询成功 effect 或每轮 refetch 时触发。禁止全局拦截所有 HTTP／Query 错误并逐条弹出。
7. 同一任务用稳定 key；key 区分动作、对象、一次提交和账号作用域。并发的不同任务互不覆盖，重复点击沿用现有 single-flight／幂等保护，不能靠屏蔽通知解决重复写入。
8. 通知状态只承载本次会话展示，不替代服务器任务、业务状态、审计或可恢复的失败明细；关闭弹框和切换页面不改变已经提交的事务。

业务使用 `src/react/hooks/useOperationFeedback.ts`：`feedback.success/info/warning/error(title, detail?, key?)` 发送 Notification；`feedback.message.success/info/warning/error(content, key?)` 发送 Message。长任务使用 `useTaskFeedback()` 的 `start/update/complete/partial/fail`，完成方法可传最终标题。Alert 由当前表单直接渲染。公共 Provider 是必需依赖，隔离组件测试应显式 mock 或挂载，不能静默回退到另一个容器。

通知随当前登录账号作用域管理：退出、切换账号和同账号重新登录时销毁旧作用域的展示，旧回调不进入新会话。弹窗退出与组件卸载后的轻量操作回调不再展示；已启动的长任务可继续完成，但关闭任务通知只关闭展示，不取消业务任务。PDF 等需要继续轮询或触发下载的任务还需在异步边界检查 `tasks.isCurrent()`，阻止旧会话自动请求或下载；同账号仅切换页面不取消后台任务。当前实现不提供持久历史通知中心。

## 错误归属、异步和重试

- 表单字段校验留在字段；无字段可定位但需要留在当前表单修复的请求错误使用 Alert。Alert 承载的同一错误不再完整重复弹出 Notification／Message。
- 409 版本冲突应持续提示刷新、重新核对或重新选择，并保留可参考的草稿；禁止静默替换版本后重提。401 会话失效沿用统一会话处理；403 不扩大权限，按当前操作上下文提示。
- 批量部分失败可以由 Notification 给出一次摘要，局部表格保留可处理的失败对象；摘要和明细各有职责，不重复堆叠同一段错误。
- “正文已保存但附件失败”分开记录两阶段结果，只重试未完成附件。结果未知的写请求先核对业务状态及既有 requestId，不自动创建新的业务请求。
- 重试按钮调用已有受版本、权限、幂等与当前作用域保护的动作；提供重试入口不代表允许绕过确认、重复发送通知邮件或重放资金操作。
- 小型操作进度留在按钮／字段；独立长任务复用 Notification 更新。列表自动刷新、轮询与加载占位保持原位，不在每次请求后弹消息。
- 局部异步反馈遵守 `useLatestRequest`／`DialogActivityContext` 的失效边界；关闭或切换对象后迟到结果不得覆盖新草稿、重开旧弹窗或向新对象报错。独立后台任务可以继续展示，但必须保留提交时的对象、账号和任务身份，结束后释放订阅。
- 退出登录或切换账号时清理原账号可见消息及其失效回调，不向新账号展示旧业务资料。通知清理不代替服务器任务取消或权限校验。
- Notification、Message 的关闭动画或 Promise 完成仅代表展示生命周期，不能据此触发业务提交、判定成功或等待后才刷新业务数据。

## 文案与资料边界

反馈由语义类型和独立文案构成，不以匹配“已”“失败”等字符串猜测级别。禁止使用一个 `notice` 字符串同时承载字段问题、长期状态、进度和最终结果；先拆清各状态的所有者，再选择组件。

通知应包含足以辨认的业务范围；后台错误先经现有错误适配再展示，不把凭据、Token、完整诊断日志、异常堆栈或数据库路径直接拼进通知。详细诊断继续进入既有日志／诊断流程，通知不是日志查看器。

深浅主题和颜色使用[颜色系统](ui-color-system.md)与[Ant 设计语言](antd-design-language.md)。维持成功、信息、警告、错误的标准图标及颜色语义；不按业务另造一套通知配色或自动等级。

## 迁移与验收

存量迁移以[全系统盘点](../analysis/ui-feedback-inventory-2026-11-02.md)为定位入口，逐条按用途迁移。先分离混合 notice，再接统一入口并移除重复的旧呈现；字段错误、持久约束、业务确认、加载及部分失败明细继续保留。

实现验证统一按[测试策略](testing-strategy.md)选择范围，不增加独立全量门禁。相关回归应覆盖：

- 成功、失败、部分成功、结果未知及重试，通知措辞与 API／SQLite／任务的实际状态一致。
- 同一动作一次结果、长任务同 key 更新、并发不相互覆盖、刷新和轮询不刷屏；Notification 与局部 Alert 无冗余重复。
- 弹窗关闭后成功仍可见，失败仍可在当前表单修复；409 草稿保留，关闭／切换对象后的旧异步结果失效。
- Message 可自动消失，必须处理的问题和部分失败明细不会随倒计时丢失；关闭通知不执行额外写入。
- 共享反馈布局变化时按 UI 分级检查桌面／窄屏、键盘、Portal 层级、主题和减少动画；未改业务事务、权限、审计及确认含义。

具体迁移和验证证据登记在[盘点与迁移记录](../analysis/ui-feedback-inventory-2026-11-02.md)，本地验证不代表生产已部署。完整发布检查继续由 Mac mini 按测试与发布契约执行。

## 官方依据

- [Ant Design Notification](https://ant.design/components/notification/)：角落通知、标题／详情／操作、同 key 更新、堆叠与关闭行为。
- [Ant Design Message](https://ant.design/components/message/)：顶部居中的轻量、自动消失的操作反馈。
- [Ant Design Alert](https://ant.design/components/alert/)：需要持续关注的原位提示容器。

核对基线为本仓库安装的 Ant Design 6.5.2 及其本地类型；在线文档可能对应更新版本，实现时以 lockfile、本地类型和组件实际能力为准。
