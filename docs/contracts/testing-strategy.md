# 测试策略

## 按改动选择验证

此处是开发验证的统一入口。按风险和实际影响选择检查，不因改动了 React、公共组件或 UI 文件就默认运行全套。

- 同一任务中的相关小改先集中完成，再做一次针对性验证；连续补充的小点合并处理，不每次编辑后启动检查。
- 已通过的检查只在其覆盖范围受后续改动影响时重跑。局部样式修正只复查受影响的显示或交互，不因此重跑前后端全量测试。
- 失败先定位原因，再重跑相关检查；只有发现跨模块影响或仍有具体风险时才扩大范围，并简要说明原因。
- 日常提交和推送完成与改动相关的验证即可，简单修改不运行完整 `npm run check`、`npm run verify:full`、生产构建或打包。结算、权限、迁移等高风险改动按影响范围扩大相关回归；不因进入提交步骤而自动执行全量检查。
- 完整开发检查放在发布前或明确要求时，由具备依赖的受管云端执行。Mac mini Runner 仅作可选手动备用，原受管发布入口及专用校验保留。同一最终代码状态和验证环境下的成功结果可复用；不重复执行其中已通过的子项，发布脚本必需的校验仍保留。用户明确要求全量验证时按该要求执行。

| 改动                               | 开发中最低验证                                                                                                                                               |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 纯 Markdown、代理指令、Skill 文本  | 修改文件的 Prettier、Markdownlint、相对链接与引用路径；Skill 校验；`git diff --check`。文档结构或配置变更按需运行 `npm run check:docs`，纯文字修改不默认构建 |
| 工具配置、依赖、脚本               | 相关工具或脚本实际运行；涉及共用门禁时验证受影响的门禁子项，不默认全量检查                                                                                   |
| 文案、间距、提示位置等局部 UI 小改 | 集中修改后确认一次受影响页面；涉及交互时检查对应鼠标、键盘行为，不默认全量测试或四档视口                                                                     |
| 纯业务计算、后端实现               | 对应 Vitest 或 Python 回归及修改文件的格式、lint；不默认 `npm run check`                                                                                     |
| React 交互                         | 对应组件或流程回归、目标页面相关操作；按需检查 TypeScript 类型与修改文件的格式、lint                                                                         |
| UI 结构、共享样式与响应式          | 下方结构性 UI 回归流程；纯文档中的 UI 说明不触发页面验收                                                                                                     |
| API、权限、缓存、迁移              | 受影响接口与领域回归；涉及权限时覆盖管理员与房间管理员，涉及写入时核对 SQLite 和审计；冒烟只覆盖相关接口                                                     |
| 打印、PDF                          | 对应模板回归、预览、A4 页数与多页定位；结算遵守下方双渲染契约                                                                                                |
| 关键业务链                         | 对应 Playwright 回归；跨域影响或发布时运行完整 `npm run test:e2e`                                                                                            |
| 大列表、查询、加载性能             | `npm run benchmark`；下方性能历史对比与分页、虚拟化、查询计划检查                                                                                            |

本地检查及本次改动引起的失败修复可连续执行，不在每一步等待确认。使用测试框架建立的临时库和 fixtures；API 冒烟或浏览器写入前核实服务和数据目录，不能将运行库当作测试库。环境缺失或历史失败要如实记录，不扩大到无关修复。

Playwright 的隔离服务默认不继承本地真实 DeepSeek key；如需受控实测须显式提供 `CAGELEDGER_E2E_DEEPSEEK_API_KEY`。普通本地开发仍读取被 Git 忽略的 `.env`，离线打包排除 `.env`。

Playwright 默认启动隔离服务；`CAGELEDGER_E2E_REUSE=1` 会复用已有实例，只有确认该实例使用可丢弃的临时库时才用于写入测试。完整回归优先使用新实例，避免残留 fixtures 导致编号冲突、状态污染或分页假设失效。失败先区分环境、测试数据和本次实现原因，再选择受影响检查重跑。

不为低风险文字改动或可逆的展示调整新增只匹配措辞、复述实现的测试。测试应验证可观察的行为或业务约束，复用已有回归覆盖。小修正由主代理完成，不为例行验证启动多代理审查，也不为单点改动新建临时工作树或安装一套依赖；仅在现有环境确有冲突、数据隔离或依赖验证需要时采用这些措施。

## 日常验证与升级规则

先看本次 diff、暂存区和未跟踪文件，再选择验证；任务交付用一句话说明“影响范围 → 实际运行的检查 → 未覆盖项”。文案、CSS 小改或提交/推送指令本身不能触发全量检查。不要将“谨慎”解释为每次都跑全部测试。

| 阶段           | 运行范围                                                        | 升级条件                                                   |
| -------------- | --------------------------------------------------------------- | ---------------------------------------------------------- |
| 编辑与本地修复 | 修改文件的静态检查；必要的单元、组件、领域/API 用例；受影响页面 | 发现调用链、共享状态或业务规则影响时扩到相关模块           |
| 提交与推送     | 复用上述同一代码状态的结果；核对新增 diff                       | 不额外运行全量；公共基础设施变更按消费者扩大范围并说明理由 |
| 发布前         | 一次质量检查＋受影响回归＋一次产物冒烟，复用有效证据            | 共享基础/高风险改动或明确要求时升级全量；如实记录选择范围  |

日常快速反馈以静态检查及选定单元测试约 2 分钟、涉及隔离 API/浏览器的单模块反馈约 10 分钟为优化目标，不是放宽断言或强制杀死合理用例的阈值。超过目标先查看慢用例、fixture、启动和资源消耗，不能靠增加并发或超时解决。高风险权限、金额、迁移、审计、跨房间转移继续覆盖受影响的前端、API、SQLite 和审计链路，不扩到无关领域。

针对性命令必须带明确目标：

```bash
# 指定测试文件；同一轮修改后集中执行
npm run test:target -- src/domain/intake.test.ts
# 按前端静态 import 关系选择关联测试
npm run test:related -- src/domain/intake.ts
# 指定 Python 模块、类或方法
npm run test:python:target -- tests.test_intake_order_identifiers
# 只有需要实际浏览器链路时才运行对应 spec，可追加 --grep 选场景
npm run test:e2e -- tests/e2e/intake.spec.ts
# 只查看将执行的命令，不启动测试或资源准入
npm run test:python:target -- tests.test_release_host_guard --dry-run
```

上述文件名按实际改动替换。`test:target`、`test:related`、`test:python:target` 未提供目标直接报错，不退回全量；未匹配用例也不能声称测试通过。`test:related` 只理解静态依赖，后端路由、动态加载、共享 fixture、全局配置和跨语言契约须补充明确目标。新增用例、此前失败的相关用例一起纳入。影响判断不清时先扩到可解释的模块集合；需要全量时先说明具体风险并使用受管入口，不能静默放大。

`npm test`、`npm run test:python` 不带目标仍表示明确运行该层全量，用于确实需要的场景；不作为代理默认开发动作。`npm run check:steps` 是受管控制器的内部串行步骤，禁止直接调用来绕过主机保护。直接执行 Vitest/Playwright 或批量 unittest 也不构成资源保护的替代；轻量脚本单测可直接指定模块进行诊断，但不能同时启动其他重任务。

## 覆盖与实际入口

按 [当前实现与兼容边界](current-baseline.md) 先确认生产入口。孤立渲染旧组件、mock 一个未被现役 View 使用的 hook，不能作为当前用户流程的缺陷或通过证据；兼容 API 的测试只证明相应接口行为。`npm run check:frontend-lifecycle` 静态核对生产依赖与历史保留清单；其解析器行为用 `node --test scripts/tests/frontend_lifecycle.test.mjs` 轻量验证，不替代角色、开关、HTTP 或浏览器验证。

## 测试用例的价值与数量

测试数量和覆盖率不是完成指标，不设每个改动必须新增几条测试的配额。新增或维护用例时，说明独特的行为/风险、最轻且足够的验证层、数据隔离和维护归属：

- 算法、字段映射、校验和边界组合优先放单元测试；事务、权限、缓存与持久化组合放领域/API 集成测试。
- E2E 保留关键用户旅程、真实浏览器交互、跨页与打印行为。已在 API 层覆盖的几十种边界不再逐条复制成 E2E；跨浏览器专项只覆盖兼容风险，不复制全部业务组合。
- Firefox/WebKit 兼容范围使用稳定 `@compat-*` 标签及 `tests/e2e/compatibility-catalog.json` 独立清单；发现目录、实际执行报告均核对完整且唯一的标签集合，不依赖测试标题文案。修改标题不得改变覆盖，新增/移除兼容场景须同时说明清单变化及风险。
- 纯布局巡检可在每个独立测试上下文中用 API 建立登录状态，登录表单本身由真实 UI 专项覆盖。不得跨用例共享可变 cookie/业务数据；截图与几何断言按实际结构风险保留。缩时结论须给同范围前后实测，不能由减少准备步骤推断节省比例。
- 纯文字、间距和提示位置调整通常复查页面即可，不新增只搜索源码字符串、逐字复制实现的测试。
- 发现重复/缓慢用例，先建立“风险 → 现有覆盖 → 替代覆盖”对照，确认等价后再合并或下移。不能为减少数字批量删测，也不把业务覆盖改成 mock 自证。
- 发布报告用于查看慢 spec、setup/teardown、重试和资源中止。失败须区分产品缺陷、数据隔离、基础设施和 flaky；禁止重跑直到变绿、自动加重试或默认更新快照。当前发布仍要求零 unexpected/flaky/skipped 的完整覆盖。

## 官方实践与本项目采用方式

以下为 2026-11-04 查阅的官方资料；采用原则，不照搬大公司集群规模或固定比例：

- [Google：Just Say No to More End-to-End Tests](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)：优先快速、稳定的小范围测试，少量 E2E 验证整体旅程。文中的比例是示例，不作为本项目配额。
- [Microsoft：Shift testing left](https://learn.microsoft.com/en-us/devops/develop/shift-left-make-testing-fast-reliable)：在足够低的层验证、保证隔离并持续治理慢和不可靠的测试。本项目用针对性单元/API 反馈替代日常全量浏览器运行。
- [Microsoft：Test Impact Analysis](https://learn.microsoft.com/en-us/azure/devops/pipelines/test/test-impact-analysis?view=azure-devops)：按改动关联选择用例，包含新增及历史失败用例，保留完整回归兜底。这里只采用选择原则，未接入其针对特定平台的 TIA 产品。
- [GitHub：Concurrency](https://docs.github.com/en/actions/concepts/workflows-and-actions/concurrency)：限制竞争同一资源的任务，避免过期验证重复消耗。CageLedger 对同一用户的宿主机使用互斥锁，不自动取消正在上传的发布；后续 CI 如接入，应按改动条件选择 job，发布任务串行。
- [Playwright：CI workers 与 global timeout](https://playwright.dev/docs/ci)：优先单 worker 和有界运行，分片不等于应在同一小内存机器同时启动。16GB Mac mini 固定一组浏览器，每个测试库仍单 worker。

## 结算汇总表双渲染链路

结算汇总表不是单一模板出口，修改时必须把以下两条链路视为同一份业务契约：

- 前端预览和“直接打印”由 `src/react/print/settlement.ts` 生成。
- 服务端 PDF、后台 PDF 任务和批量导出由 `server_app/pdf/documents.py` 生成。

涉及字段、计费结果、汇总、分页、列宽、说明或页脚的修改，需要同时更新两端实现，并分别在 `src/react/print/printTemplates.test.ts` 和 `tests/test_pdf_exports.py` 添加等价断言。多页结算单至少覆盖：第一页汇总包含后续页同品种伦理，逐日笼数、减免、梯度、缴纳金额和单项合计一致，预览与导出 PDF 的物理页数及页码一致。只验证其中一个出口不得作为完成依据。

### 浏览器诊断与运行异常

共用 `tests/e2e/fixtures.ts` 继续将未预期的应用 `console.warn`、`console.error` 和未捕获页面异常作为失败。Firefox 原生的 scroll-linked-effects 提示只有同时匹配 Firefox 引擎、完整原生包装文本、当前应用文档 URL、零行号和原生列号时，才单独记录为 `native-browser-performance-diagnostics` 报告附件；其他内容或来源仍失败。分类器有反例单测，并以真实页面日志验证：应用代码即使输出同样文字，也不能被重新分类。

该诊断说明浏览器检测到可能影响异步滚动的效果，并不等于已测得卡顿或运行异常；保留附件供性能分析，不能宣称提示已消失或性能问题已修复。相关页面仍需验证实际滚轮、工具栏与焦点稳定，以及返回后的位置恢复。Mozilla 的语义见 [Scroll-linked effects](https://firefox-source-docs.mozilla.org/performance/scroll-linked_effects.html)。仅用于验证诊断分类器的反例用例可以使用原始 Playwright 捕获故意产生的警告/异常；业务流程仍使用共用 fixture。

## 完整基础检查

`npm run verify:quality` 执行格式、lint、类型和项目契约检查；不运行测试或生产构建。`npm run check` 在此基础上显式执行全部 Vitest／Python 单元与集成测试；文档站生产构建已移到统一 build 阶段，不在 check 中重复。简单修改只执行上方矩阵中的相关检查。开发依赖需要提前安装：

Vitest 文件并发上限为1，避免 M4 16GB 上多个 Ant Design／JSDOM 大表格与弹窗测试同时争用CPU和内存；保留原有默认超时、断言、全部用例与失败退出规则，不以减少覆盖或增加超时换取通过。

```bash
npm ci
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
npm run check
```

`npm run dev` 和 `npm run test:e2e` 使用项目 `.venv` 的 Python 启动 API，避免继承 macOS 系统 Python。`CAGELEDGER_PYTHON_BIN` 可指定其他 Python 3.13 可执行文件。

## UI 回归流程

实际 UI 改动按以下两档选择验证，覆盖受影响组件和状态；同一轮修改完成后统一执行。

- 局部小改：文案、间距、按钮或提示位置调整，以及复用既有组件且不改变布局机制的小调整，默认只在目标页面确认一次。只检查本次涉及的交互；出现窄屏、溢出或焦点问题时再补对应视口或状态，不默认截图矩阵、computed style 报告和全套回归。
- 结构性改动：页面布局重构、响应式断点、导航机制、滚动或 Portal 定位，以及影响多个页面的公共布局、主题或控件样式，执行下面的四档验收。范围不以修改行数判断。

四档验收要求如下。`npm run check` 已包含 Ant Design、样式归属与 Stylelint 检查；开发中只在相关规则有变化或定位问题时单独运行，完整检查通过后无需重复这些子项。

- 定位目标组件的 class、data attribute、媒体查询和导入顺序，确认唯一布局归属。视觉差异回溯样式来源和级联，不新增同类覆盖层。
- 在桌面、1180px、760px、手机横屏验证目标页面实际适用的默认、焦点、禁用、加载和长文本状态。
- 检查浏览器 computed style 与容器溢出，重点覆盖 `display`、网格列、最小宽度、间距、定位和层级。
- 关键流程有变化时补充或更新对应 Playwright 断言，版式变化保留截图；修改完成后运行 `git diff --check`，完整检查留到发布前在 Codex 云端执行。
- 按 [`ui-change-evidence.md`](../templates/ui-change-evidence.md) 保存组件归属、四档视口、溢出与 computed style 证据。

涉及表单尺寸或样式冲突时，读取受影响的 DatePicker、Select、Input 的 computed style：桌面默认 32px、紧凑 24px；手机输入控件 40px/16px 字号、按钮触控目标至少 44px。同一行保持对齐，只读信息优先呈现为文本。主题和动效由 `src/theme/visual-system.mjs` 派生；`node scripts/generate_theme.mjs --check` 校验应用及文档变量没有漂移。跨断点、主题或减少动画切换时同时检查草稿、焦点与浮层。涉及 Portal 定位或样式时检查 `.app-modal-root` 的实际作用域；保持单一纵向滚动所有者。修改交互、权限、打印、导出、缓存或加载链路时，浏览器检查实际用户入口中的受影响路径。

## 云端交付验证流程

默认按风险选测试；不能因为提交、版本标签或“发布”二字自动重复所有测试。

| 阶段       | 默认执行                                  | 才需要补充的情况                                                |
| ---------- | ----------------------------------------- | --------------------------------------------------------------- |
| 选择范围   | 冻结版本/更新记录，查看 diff 和已有结果   | 无法判断影响时扩大到明确的消费者模块                            |
| 质量与回归 | 一次静态质量检查及受影响的单元/API测试    | 权限、结算、迁移、共享状态变更补相应跨层回归                    |
| UI / PDF   | 有对应改动才验证目标页面或渲染出口        | 全局样式、浏览器API、路由、打印机制或浏览器依赖变化才补兼容专项 |
| 统一构建   | 应用＋文档构建一次，生成内容凭据          | 源码、Node/依赖或构建输出变化才重建                             |
| 软件包     | 源码包和ARM64镜像复用同一份已验证前端     | 独立 Docker 构建仍可自行构建前端                                |
| 产物冒烟   | 对最终新产物验证版本、平台、页面/API      | Python/系统依赖、Dockerfile或转换器变化补ARM执行/Writer/PDF专项 |
| 上传       | 首尾权限/来源复核，每个新附件完整回读一次 | 不明结果、附件身份变化或显式审计才重读已成功附件                |

同一个缺陷的相同边界组合只保留最轻且充分的测试层；业务API已经覆盖的组合不再在每个浏览器重复枚举。真实UI旅程、权限写入、金额/迁移/审计断言和结算双渲染等独特风险不按测试数量批量删除。纯源码字符串匹配、逐字复述实现或只检查测试命名的用例不作为新增覆盖。

### 结果复用与失效

- `verify_local.py` 自动复用本机的单元/Python/基础检查成功证据：源码内容、选中命令/范围、相关Node/Python及外部工具输入一致，原日志存在且SHA未变才有效。提交本身没有改变内容时，不单独使结果失效。日志丢失、修改、零用例、失败或跳过的结果不可当成完整成功缓存。
- 报告区分 `passed` 与 `reused`，复用记录指向原始日志；不是重新执行一次的证明。需要主动排查环境或不稳定用例时使用 `--no-reuse`，只重跑所选范围。
- 浏览器结构化覆盖由专用凭据管理，不用普通命令退出码缓存替代。完整目录JSON按每引擎内容SHA及源码/运行时指纹复用，损坏则重新发现；实际覆盖缺失才重跑相关测试。调度上限改变不使成功覆盖失效，实际worker、引擎、分片和用例集仍参与标识。
- 同一进程内，浏览器安装包与 Mac 转换器只在首次或完整安装元数据变化时重新读取全部字节及验证供应商签名；路径、文件列表或 ctime 变化立即失效，新进程仍完整验证。源码、构建产物和远端附件不走该工具缓存。
- 应用与文档共享 `frontend_build.py` 凭据：源码/Node/依赖和 `web-dist` 完整内容一致才复用。源码包与容器入口都复核该凭据；不提供盲信“目录已存在”的跳过开关。
- 远端附件按不可变ID/URL/大小和已完整回读的SHA证据复用；`unknown`、无凭据、身份变化必须重新读字节。`publish:cloud -- --audit-remote` 显式审计所有附件，可发现远端身份不变的存储内容损坏。

## 显式全量与 Mac 手动备用

`npm run verify:full` 仍保留完整范围：基础质量＋全部单元/API → 共享生产构建 → Chromium完整回归 → Firefox/WebKit兼容专项。没有重复的文档构建。只有实际完成且结构化报告、覆盖集合、退出码均有效时才称完整通过；不能在缺库时跳过引擎。

旧 `release:local` 是显式选择的 Mac 完整正式发布配置，不是云端普通构建/开发草稿的默认前置流程。它保留供应商转换器签名/公证、发布引用和完整交付门禁。Mac 16GB 一次仅一组浏览器，每个测试库单worker；云端按cgroup保护。两个平台都保留宿主互斥、临时SQLite、独立端口、完整报告和仅清理本任务进程的规则。

版本、源码内容、依赖、实际引擎/转换器或报告变化会失效对应证据；调度预算变化本身不触发全回归。完整Chromium分片必须核对用例ID并集等于目录、交集为空；各引擎报告必须完整，unexpected/flaky/skipped为零。失败先诊断原因，保留未受影响的有效结果，不用无限重试、增加超时或关闭资源保护来变绿。

正式管线同版本、同状态目录续跑；上传结果不明先核对远端，不覆盖已有tag、镜像或附件。源码包已有的正式build凭据复用继续保留。资源策略、签名与恢复细节见 [发布工程](release-engineering.md) 和受管脚本，历史M4分片耗时估算不再作为云端门禁。

## 业务回归

数据库真实备份的兼容核查使用 `npm run verify:database`，参数、隔离与覆盖见 [数据库副本核查契约](database-copy-review.md)。仅对显式提供的离线备份生成新副本，不纳入默认检查。旧写入事务改动另以真实双连接验证锁前读取、版本冲突、旧客户端缺省版本、审计回滚和跨记录修改保留；接口及浏览器回归继续覆盖实际保存入口。

数据库与附件的离线备份恢复演练使用 `npm run verify:restore`，输入同批备份、创建备份包及独立恢复目录、核对业务与附件的边界见[备份恢复演练契约](backup-restore-drill.md)。不纳入默认检查，不操作原数据库或附件，不自动运行生产恢复。

- 笼卡：识别、保存、打印、接收、回退和待进驻生成。
- 笼位：授权房间、预留、正式入驻、设为空和 Animal Record ID 延续。
- 数量统计表：多类型录入、日期、转入转出镜像、保存、预览和导出。
- 结算：按 PI 合表、IACUC 有效期、逐日减免、全额减免、PDF 和流程发起。
- 单据跟踪：结算流程筛选、交回登记、锁定归档、补录报销单和撤回/撤销。
- 权限：管理员与房间管理员分别验证前端入口和 API 状态码。
- 系统状态：管理员性能快照与历史记录、PDF 队列与缓存指标、手动刷新、普通账号不请求指标、空样本、四档视口与 Axe。
- 性能改动：缓存、索引、SQLite 查询、PDF 渲染、批量操作或首屏加载改动前后，读取相同时间窗口的 `/api/system/performance-history`，记录版本、HTTP/SQLite P95、慢请求、锁错误和结论；同时运行 `npm run benchmark`。历史数据只能用于管理员趋势与验收，采样不得进入请求链路，也不得包含用户、请求参数或 SQL。
- 共用结算与应收查询：分别测首次读取和稳定读取的耗时、SQL次数及查询计划，覆盖列表、列筛选、金额排序和应收详情；使用相同来源的独立副本对比基准与当前代码。原副本缺少技术服务记录时，在独立测试副本补充混合费用场景并单列结果。基准副本不能预先带入当前代码新增的索引。核对应收读取同步、金额、权限和审计等价；SQL次数下降后，单次SQLite操作P95的样本构成也会改变，不能单独用该指标判定整体快慢。
- 候选账单批量预取还需覆盖缓存失效后的金额排序、最新流程的同时间排序、缺失或损坏快照及逐日行顺序，完整快照校验不能因列表提速而省略。应收纯解析缓存必须按完整来源内容隔离，覆盖同版本改价和不同数据库复用相同ID；每次读取来源及原同步审计时机保持不变。
- 月度汇总提速同时核对各月份 Excel 单元格值、类型、公式、金额格式、字体、边框、对齐、列宽、行高及空表范围；混合费用、仅技术服务月份、零金额和跨设施的金额归属规则保持不变。

## 发布验证分工

Codex 云端负责日常开发、验收、按影响范围的测试和交付任务的软件包构建；代码及产物推送到 Gitea，由 Gitea 托管代码和软件包。Mac mini Runner 仅作可选手动备用。简单修改不默认全量检查；交付按风险补充检查，完整回归仅在明确要求或共享基础变化需要时执行。生产目标 DS223（aarch64），后续只构建 `linux/arm64`；离线源码包继续保留，历史 AMD64 制品不删除。交付记录实际检查、产物和未覆盖项。

只有明确交付任务才通过云端 `package:managed` 串行生成源码包与 ARM64 镜像包，普通开发不因提交或代码推送自动打包。测试证据、构建源码和上传产物必须对应同一最终状态及来源 revision；已有版本制品不覆盖。Gitea 私有仓库开发构建草稿托管不等同于完整正式发布门禁，也不自动部署 NAS。

可选 Mac mini Runner 使用原生 host 标签、capacity 1，并共用宿主锁和资源保护；工作流仅允许手动触发。部署见 [macos-gitea-runner.md](macos-gitea-runner.md)。

Mac mini `release:local` 保留正式发版能力及平台专用转换器校验。云端普通打包不依赖该入口。当前云端 WebKit 系统库受限，不能报告完整跨浏览器门禁或 Linux 正式发布管线已全部适配；提交、推送、产物上传、正式发版与生产部署按各自授权执行。云端操作见 [cloud-development.md](cloud-development.md)。

发布验证覆盖最终待打标签和构建的代码状态，包括版本及更新记录的修改。发布记录保留来源提交、门禁结果和最终标签；验证后的新改动按受影响范围重新检查，不复用已失效的结果。

## Codex Linux 云环境

完整环境、工具安装、分支与打包入口见 [cloud-development.md](cloud-development.md)。
所有 `verify_local.py` 模式在 Linux 上使用 cgroup v2 资源监测；macOS 保持原生保护。
仅检查所选命令实际需要的能力：quality不要求浏览器；单元/API按用例依赖；check的PDF测试使用锁定Chromium/转换器；full或compat才要求对应Firefox/WebKit。选中引擎缺库仍明确失败。
日常定向命令只覆盖所选目标，不能冒充完整门禁。

内存余量按 cgroup 工作集计算（`memory.current - inactive_file`），排除可回收文件缓存；
原始用量、工作集、OOM 和内存上限事件均保留在证据中。准入需至少 35% 余量，运行中至少 20%，
且均至少 1 GiB；新增 OOM 事件、
swap 增长超过 512 MiB 或遥测心跳超过 90 秒时停止。真正执行的全量、构建及浏览器任务保留 60 秒稳定观察；全部复用时不重复准入等待，
定向单元/API 测试只做一次准入检查。互斥锁、单 worker、进程回收、隔离数据库和证据目录均保留。

```bash
source scripts/cloud_env.sh
npm run test:python:target -- tests.test_linux_test_guard tests.test_verification_workflow
npm run test:target -- src/domain/intake.test.ts src/react/api/client.test.ts
npm run test:e2e -- tests/e2e/login-navigation.spec.ts
```

没有浏览器、缺少库或资源中止应报告失败或未完成，不禁用保护、不跳过断言。
