# 测试策略

## 按改动选择验证

此处是开发验证的统一入口。按风险和实际影响选择检查，不因改动了 React、公共组件或 UI 文件就默认运行全套。

- 同一任务中的相关小改先集中完成，再做一次针对性验证；连续补充的小点合并处理，不每次编辑后启动检查。
- 已通过的检查只在其覆盖范围受后续改动影响时重跑。局部样式修正只复查受影响的显示或交互，不因此重跑前后端全量测试。
- 失败先定位原因，再重跑相关检查；只有发现跨模块影响或仍有具体风险时才扩大范围，并简要说明原因。
- 日常提交和推送完成与改动相关的验证即可，简单修改不运行完整 `npm run check`、`npm run verify:full`、生产构建或打包。结算、权限、迁移等高风险改动按影响范围扩大相关回归；不因进入提交步骤而自动执行全量检查。
- 完整检查放在发布前，由 Mac mini 执行发布脚本及完整门禁。同一最终代码状态和验证环境下的成功结果可复用；不重复执行其中已通过的子项，发布脚本必需的校验仍保留。用户明确要求全量验证时按该要求执行。

| 改动                               | 开发中最低验证                                                                                                                                               |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 纯 Markdown、代理指令、Skill 文本  | 修改文件的 Prettier、Markdownlint、相对链接与引用路径；Skill 校验；`git diff --check`。文档结构或配置变更按需运行 `npm run check:docs`，纯文字修改不默认构建 |
| 工具配置、依赖、脚本               | 相关工具或脚本实际运行；涉及共用门禁时验证受影响的门禁子项，不默认全量检查                                                                                   |
| 文案、间距、提示位置等局部 UI 小改 | 集中修改后确认一次受影响页面；涉及交互时检查对应鼠标、键盘行为，不默认全量测试或四档视口                                                                     |
| 纯业务计算、后端实现               | 对应 Vitest 或 Python 回归及修改文件的格式、lint；不默认 `npm run check`                                                                                     |
| React 交互                         | 对应组件或流程回归、目标页面相关操作；按需检查 TypeScript 类型与修改文件的格式、lint                                                                         |
| UI 结构、共享样式与响应式          | 下方结构性 UI 回归流程；纯文档中的 UI 说明不触发页面验收                                                                                                     |
| API、权限、缓存、迁移              | 受影响接口与领域回归；涉及权限时覆盖管理员与房间管理员，涉及写入时核对 SQLite 和审计；冒烟只覆盖相关接口                                                     |
| 打印、PDF                          | 对应模板回归、预览、A4 页数与多页定位；结算遵守下方双渲染契约                                                                                                |
| 关键业务链                         | 对应 Playwright 回归；跨域影响或发布时运行完整 `npm run test:e2e`                                                                                            |
| 大列表、查询、加载性能             | `npm run benchmark`；下方性能历史对比与分页、虚拟化、查询计划检查                                                                                            |

本地检查及本次改动引起的失败修复可连续执行，不在每一步等待确认。使用测试框架建立的临时库和 fixtures；API 冒烟或浏览器写入前核实服务和数据目录，不能将运行库当作测试库。环境缺失或历史失败要如实记录，不扩大到无关修复。

Playwright 默认启动隔离服务；`CAGELEDGER_E2E_REUSE=1` 会复用已有实例，只有确认该实例使用可丢弃的临时库时才用于写入测试。完整回归优先使用新实例，避免残留 fixtures 导致编号冲突、状态污染或分页假设失效。失败先区分环境、测试数据和本次实现原因，再选择受影响检查重跑。

不为低风险文字改动或可逆的展示调整新增只匹配措辞、复述实现的测试。测试应验证可观察的行为或业务约束，复用已有回归覆盖。小修正由主代理完成，不为例行验证启动多代理审查，也不为单点改动新建临时工作树或安装一套依赖；仅在现有环境确有冲突、数据隔离或依赖验证需要时采用这些措施。

## 结算汇总表双渲染链路

结算汇总表不是单一模板出口，修改时必须把以下两条链路视为同一份业务契约：

- 前端预览和“直接打印”由 `src/react/print/settlement.ts` 生成。
- 服务端 PDF、后台 PDF 任务和批量导出由 `server_app/pdf/documents.py` 生成。

涉及字段、计费结果、汇总、分页、列宽、说明或页脚的修改，需要同时更新两端实现，并分别在 `src/react/print/printTemplates.test.ts` 和 `tests/test_pdf_exports.py` 添加等价断言。多页结算单至少覆盖：第一页汇总包含后续页同品种伦理，逐日笼数、减免、梯度、缴纳金额和单项合计一致，预览与导出 PDF 的物理页数及页码一致。只验证其中一个出口不得作为完成依据。

### 浏览器诊断与运行异常

共用 `tests/e2e/fixtures.ts` 继续将未预期的应用 `console.warn`、`console.error` 和未捕获页面异常作为失败。Firefox 原生的 scroll-linked-effects 提示只有同时匹配 Firefox 引擎、完整原生包装文本、当前应用文档 URL、零行号和原生列号时，才单独记录为 `native-browser-performance-diagnostics` 报告附件；其他内容或来源仍失败。分类器有反例单测，并以真实页面日志验证：应用代码即使输出同样文字，也不能被重新分类。

该诊断说明浏览器检测到可能影响异步滚动的效果，并不等于已测得卡顿或运行异常；保留附件供性能分析，不能宣称提示已消失或性能问题已修复。相关页面仍需验证实际滚轮、工具栏与焦点稳定，以及返回后的位置恢复。Mozilla 的语义见 [Scroll-linked effects](https://firefox-source-docs.mozilla.org/performance/scroll-linked_effects.html)。仅用于验证诊断分类器的反例用例可以使用原始 Playwright 捕获故意产生的警告/异常；业务流程仍使用共用 fixture。

## 完整基础检查

`npm run check` 执行格式检查、全部 lint、TypeScript 类型检查、Vitest、Python unittest、项目契约检查与文档构建，是 Mac mini 发布前的基础检查，不是日常提交和推送的必需命令。简单修改只执行上方矩阵中的相关检查。开发依赖需要提前安装：

```bash
npm ci
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
npm run check
```

`npm run dev` 和 `npm run test:e2e` 使用项目 `.venv` 的 Python 启动 API，避免继承 macOS 系统 Python。`CAGELEDGER_PYTHON_BIN` 可指定其他 Python 3.13 可执行文件。

## UI 回归流程

实际 UI 改动按以下两档选择验证，覆盖受影响组件和状态；同一轮修改完成后统一执行。

- 局部小改：文案、间距、按钮或提示位置调整，以及复用既有组件且不改变布局机制的小调整，默认只在目标页面确认一次。只检查本次涉及的交互；出现窄屏、溢出或焦点问题时再补对应视口或状态，不默认截图矩阵、computed style 报告和全套回归。
- 结构性改动：页面布局重构、响应式断点、导航机制、滚动或 Portal 定位，以及影响多个页面的公共布局、主题或控件样式，执行下面的四档验收。范围不以修改行数判断。

四档验收要求如下。`npm run check` 已包含 Ant Design、样式归属与 Stylelint 检查；开发中只在相关规则有变化或定位问题时单独运行，完整检查通过后无需重复这些子项。

- 定位目标组件的 class、data attribute、媒体查询和导入顺序，确认唯一布局归属。视觉差异回溯样式来源和级联，不新增同类覆盖层。
- 在桌面、1180px、760px、手机横屏验证目标页面实际适用的默认、焦点、禁用、加载和长文本状态。
- 检查浏览器 computed style 与容器溢出，重点覆盖 `display`、网格列、最小宽度、间距、定位和层级。
- 关键流程有变化时补充或更新对应 Playwright 断言，版式变化保留截图；修改完成后运行 `git diff --check`，完整检查留到发布前在 Mac mini 执行。
- 按 [`ui-change-evidence.md`](../templates/ui-change-evidence.md) 保存组件归属、四档视口、溢出与 computed style 证据。

涉及表单尺寸或样式冲突时，读取受影响的 DatePicker、Select、Input 的 computed style：桌面默认 32px、紧凑 24px；手机输入控件 40px/16px 字号、按钮触控目标至少 44px。同一行保持对齐，只读信息优先呈现为文本。主题和动效由 `src/theme/visual-system.mjs` 派生；`node scripts/generate_theme.mjs --check` 校验应用及文档变量没有漂移。跨断点、主题或减少动画切换时同时检查草稿、焦点与浮层。涉及 Portal 定位或样式时检查 `.app-modal-root` 的实际作用域；保持单一纵向滚动所有者。修改交互、权限、打印、导出、缓存或加载链路时，浏览器检查实际用户入口中的受影响路径。

## 完整门禁

完整发布门禁包含基础质量检查、React 应用与 VitePress 文档站生产构建、Chromium 完整 Playwright，以及 Firefox／WebKit 桌面兼容专项。E2E 使用临时 SQLite，测试数据不会写入正式数据库。当前 `npm run verify:full` 仍按上述顺序串行执行，作为兼容和低资源回退入口；Mac mini 发布优先按下方 M4 配置编排等价的并行检查，不能把文档约定当作现有脚本已自动分片。

桌面专项通过 `npm run test:e2e:compat` 单独运行；首次使用执行 `npx playwright install firefox webkit` 安装当前锁定 Playwright 配套的浏览器，不升级依赖。专项串行启动两个独立临时服务及数据库，单 worker、零重试，不允许复用开发服务。默认端口为 5193/5194/5195 与 5203/5204/5205，`CAGELEDGER_COMPAT_PORT` 可调整起始端口；`CAGELEDGER_COMPAT_OUTPUT_DIR` 指定日志报告、截图及样式证据目录，默认位于 `test-results/desktop-compat`。

专项包含 1440px／1180px 下的全部工作入口、公开页面和代表性表单、筛选、权限、异步反馈。Chromium 专用 CDP 和模拟相机用例继续由全量回归覆盖，WebKit 结果仅表示引擎自动化通过，不等同真实 Safari 或手机设备实测。失败不得通过跳过或删除断言消除；重试通过项须定位原因，并对相关用例连续复验两次。

Chromium 设置 `failOnFlakyTests`，重试通过仍使完整门禁失败，避免不稳定用例被报告为全绿；修复后重新取得完整成功结果。`CAGELEDGER_E2E_OUTPUT_DIR` 可将 Chromium 截图、trace、JSON 和 HTML 报告保存至独立目录，不覆盖此前失败证据。

VitePress 文档使用 `wiki/` 作为唯一源目录。`npm run release:notes:sync` 从 `wiki/更新日志.md` 生成系统“关于”页使用的更新记录；发布脚本同时校验 Markdown 版本条目和生成结果。

### M4 16GB 发布并行配置

此配置适用于 Apple M4、10核CPU（4个性能核＋6个能效核）、16GB内存的 Mac mini。并发单位是一组浏览器测试及其 Vite、Python API、文档服务，不是操作系统线程数，也不是代理数量。

默认同时运行 **3个Chromium分片＋1条Firefox→WebKit串行兼容链**，最多4组浏览器任务。每组保持 `workers=1`、`fullyParallel=false`；通过独立服务与数据库并行，不能直接在同一测试库上增加worker。4个Chromium分片再加兼容链会达到5组，不能仅根据10个逻辑核心就设为默认；提高上限前需测量资源和整个门禁耗时，并连续两次完整通过且没有不稳定用例。

v1.14.0的历史报告包含266项Chromium用例：两片实测约12.0、13.8分钟；Firefox和WebKit串行合计约7.7分钟。用同一批历史时长映射到Playwright实际默认分组，3片为94／85／87项，累计测试时长约8.0／8.1／9.7分钟；4片的最长组仍约8.1分钟。它们是历史估算，未计入新并发下的启动和资源争用，不能承诺等比例加速；首次采用3片时记录实际墙钟、峰值内存压力及交换空间增量后再校准。

#### 阶段与资源预算

- 先在隔离发布检出中确定版本、更新记录和依赖，再执行基础检查与生产构建。同一检出中的 `npm run check`、`npm run build` 和离线打包不能相互重叠：它们会复用文档构建目录，构建还会生成更新记录及应用产物。
- 浏览器阶段按4组上限同时启动三片Chromium和兼容链；不同时启动Docker镜像构建、另一次完整门禁或本地大模型推理。常驻服务不应被擅自停止，资源不足时降低测试并发。
- 至少给系统和日常应用预留约4GB资源预算；这不是四组任务的内存用量保证。若系统内存压力持续进入警告／严重状态、交换空间持续增长或桌面响应明显变慢，停止启动新任务，降到2片Chromium＋兼容链，必要时串行。保留已完成结果并在报告中记录降级原因，不通过增大超时掩盖资源争用。
- 只有全部必需检查成功，才进入发布提交、标签、镜像与Release上传；Git写入及同一标签的发布操作保持串行。

#### 分片隔离与调用

以下是默认端口示例；启动前检查占用，冲突时为本次任务整体分配另一组空闲端口，不结束占用端口的未知进程。

| 任务                    | 页面／API／文档端口 | 证据子目录        |
| ----------------------- | ------------------- | ----------------- |
| Chromium 1/3            | 5613／5614／5615    | `chromium-1-of-3` |
| Chromium 2/3            | 5623／5624／5625    | `chromium-2-of-3` |
| Chromium 3/3            | 5633／5634／5635    | `chromium-3-of-3` |
| Firefox                 | 5643／5644／5645    | `compat/firefox`  |
| WebKit（Firefox结束后） | 5653／5654／5655    | `compat/webkit`   |

每片必须独立设置 `CAGELEDGER_E2E_PORT`、`CAGELEDGER_E2E_API_PORT`、`CAGELEDGER_DOCS_PORT`、`CAGELEDGER_E2E_OUTPUT_DIR`，并使用 `CAGELEDGER_E2E_REUSE=0`。Playwright读取的是 `E2E_*` 端口变量，再传给开发服务；只设置 `CAGELEDGER_DEV_*` 会落回默认测试端口，造成分片冲突。启动后核对health中的数据库路径，确认各片都是不同的临时库；不得使用原始数据库、附件或普通开发实例。

以下命令分别作为受管并行任务执行，不能简单顺序粘贴后声称已经并行。`release_evidence_dir` 由调用方设置为本次运行独立的绝对证据目录，不是现有发布脚本的配置开关。

```bash
# Chromium 1/3；其余两片按表替换端口、目录和 --shard。
: "${release_evidence_dir:?请先设置本次独立证据目录}"
CAGELEDGER_E2E_PORT=5613 CAGELEDGER_E2E_API_PORT=5614 CAGELEDGER_DOCS_PORT=5615 \
  CAGELEDGER_E2E_REUSE=0 CAGELEDGER_E2E_OUTPUT_DIR="$release_evidence_dir/chromium-1-of-3" \
  npx playwright test --shard=1/3 --workers=1 --retries=0

# 与Chromium分片并行，脚本内部仍依次执行Firefox和WebKit。
CAGELEDGER_COMPAT_PORT=5643 CAGELEDGER_COMPAT_OUTPUT_DIR="$release_evidence_dir/compat" \
  npm run test:e2e:compat -- --retries=0
```

使用能等待子进程结束并收集退出码的编排器或多个前台任务。不能用未经管理的 `command &` 后退出父进程；仅看到PID、端口监听或部分日志不算检查完成。中断时只清理本次任务创建的进程组，保留失败日志、trace及报告。运行期间不修改同一检出的源文件或生成产物；需要修复时先结束受影响任务，再按影响范围复验。

#### 汇总与复用

- 分片前用锁定的Playwright执行 `npx playwright test --list --reporter=json` 保存完整目录。汇总时核对各片用例ID的并集等于目录、交集为空，同时保留两个兼容引擎的独立结果；不能只相加通过数量。
- 每项任务必须有退出码和完整JSON报告，启动失败、进程被中断、报告缺失或用例未执行均不能放行。所有必需用例应完成，`unexpected`、`flaky`、`skipped` 均为0；正式门禁使用零自动重试，修复后的定向重跑不能替代缺失的完整覆盖。
- 记录版本、构建号、来源提交及未提交发布文件指纹、依赖锁文件、分片拓扑、命令、端口、临时库路径、起止时间与资源情况。失败时保留其他有效分片结果，只复验受影响范围；改变用例集合、分片拓扑或共享配置时重新判断整组覆盖，不混用无法对应的报告。
- 同一发布输入的完整并行证据通过后，不再额外串行运行一次 `npm run verify:full`。可在核对证据后使用 `release:local --skip-full-verify` 复用已完成的完整门禁；该选项仍会执行 `npm run check` 和离线包构建，脚本要求的检查保留。进一步消除重复检查或构建需要单独实现输入指纹校验与证据复用，不能仅凭这份约束跳过。

## 业务回归

数据库真实备份的兼容核查使用 `npm run verify:database`，参数、隔离与覆盖见 [数据库副本核查契约](database-copy-review.md)。仅对显式提供的离线备份生成新副本，不纳入默认检查。旧写入事务改动另以真实双连接验证锁前读取、版本冲突、旧客户端缺省版本、审计回滚和跨记录修改保留；接口及浏览器回归继续覆盖实际保存入口。

数据库与附件的离线备份恢复演练使用 `npm run verify:restore`，输入同批备份、创建备份包及独立恢复目录、核对业务与附件的边界见[备份恢复演练契约](backup-restore-drill.md)。不纳入默认检查，不操作原数据库或附件，不自动运行生产恢复。

- 笼卡：识别、保存、打印、接收、回退和待进驻生成。
- 笼位：授权房间、预留、正式入驻、设为空和 Animal Record ID 延续。
- 数量统计表：多类型录入、日期、转入转出镜像、保存、预览和导出。

## 发布验证分工

MacBook 默认执行代码修改、按影响范围的针对性验证、提交和推送到 Gitea；简单修改不执行完整检查和发布构建，不自动转交 Mac mini 跑全量验证。交付记录已执行的检查和留待发布验证的项目。

Mac mini 从 Gitea 同步待发布代码，在发布前执行格式、lint、类型、Vitest、Python 全量测试、应用与文档生产构建、Playwright、PDF/打印验收、API 冒烟和性能 benchmark，并负责版本、标签、离线包、容器镜像、Release 上传与 Wiki 同步。浏览器报告与测试结果保留在本地发布验证记录中。Gitea 保存 Git 代码、Wiki 迁移页、Release 资产和容器镜像。

发布验证覆盖最终待打标签和构建的代码状态，包括版本及更新记录的修改。发布记录保留来源提交、门禁结果和最终标签；验证后的新改动按受影响范围重新检查，不复用已失效的结果。
