# PDF 浏览器生命周期修复验收

本批在 `codex/performance-post-1.17.1` 上独立完成，前一轮 14 项拆分的提交 `e2f65e6`、归档 `61b6feb` 及其验收记录保留。应用与测试修复提交为 `1d93dec7f8f7eccdb4f821b0bc179154bdc1a13f`。仅本地修改、提交和隔离验证，未推送、发布、部署，也未连接生产或修改生产数据。

## 根因与修复

- **已验证的范围区别**：原版本直接收到 Python PID 的 SIGTERM 时，驱动的管道 EOF 清理也会结束浏览器；原版对照退出码为 -15、8 个已登记后代均退出。不能据此声称原版本所有正常 SIGTERM 都会泄漏。
- 前轮实际发现并按所有权证明清理的 7 组浏览器，与隔离验收启动时段对应。本地安装的 Playwright 源码显示，未配置 `webServer.gracefulShutdown` 时默认收尾落入进程组 SIGKILL；浏览器另有自己的进程组，服务与驱动被同时强杀时不能依赖 EOF 清理。该机制与原有残留证据吻合；本次未主动强杀服务复现。
- PDF renderer 原本没有显式退出入口；同步 Playwright 上下文初始化异常也在外层循环之外，会使已接收的请求留在队列中，直到超时。最终提交的确定性依赖故障对照中，旧版等待 160.2ms 后超时且 queueDepth=1，修复版约 0.42ms 返回初始化失败且 queueDepth=0。此探针的 150ms 预算仅用于假依赖对照，未修改应用或浏览器测试预算。
- renderer 现将任务接收和线程启动放在同一锁内；退出关闭接收、释放排队请求、等待当前渲染结束，由所有者工作线程关闭 browser/context/driver。初始化、部分建页和关闭失败也释放等待方。重复退出幂等，并有进程正常退出的 atexit 兜底。
- API 的 SIGINT/SIGTERM handler 只设置退出标志，避免在锁或线程启动窗口抛异步异常。HTTP 接收循环由独立线程运行，主线程调用 `shutdown` 并等待，再关闭 PDF renderer；端口绑定失败和预热期间退出也执行清理。
- 开发启动器只使用自己持有的 ChildProcess 句柄发送正常 SIGTERM，等待子服务退出后才删除生成数据。Playwright 的服务收尾单独设置 SIGTERM / 150 秒宽限；启动仍 120 秒，本地业务用例仍 30 秒、expect 5 秒，本次命令均单 worker、零重试。没有改核算、权限、审计、数据结构、PDF 模板/输出选项或服务公共 API。

## PDF 输出与性能

同一机器、同一生成数据和 HTTP 入口，分别测数量表与结算单；基线每类 6 次（首份单列、热样本 5），最终三轮每类共 18 次（热样本 15）。36 份最终 PDF 的页数与提取文本 SHA-256 均与原基线一致；PDF 原始字节包含生成元数据，未要求字节相同。多页 A4、金额和页码另由真实浏览器业务用例断言。

| 指标                          |    基线 |              最终 |
| ----------------------------- | ------: | ----------------: |
| 数量表热渲染中位数            | 77.11ms | 77.92ms（+1.05%） |
| 结算单热渲染中位数            | 86.45ms | 86.76ms（+0.37%） |
| 数量表热渲染 nearest-rank P95 | 79.53ms |           95.27ms |
| 结算单热渲染 nearest-rank P95 | 92.21ms |           90.09ms |

数量表首份基线 1056.5ms，最终三轮 856.6 / 550.1 / 545.4ms；结算单在同一个已预热浏览器内首次渲染，不能称为独立浏览器冷启动。未调整渲染选项或性能阈值。热中位数接近，但数量表尾部有波动，且两组样本量不同，不能声称统计上证明所有负载均无退化，也不将冷缓存差异宣传为性能提升。

## 失败记录与限制

- `lifecycle-unit-reviewed.log` 首次出现 1 个测试 fake 失败：未启动 Thread mock 的 `is_alive()` 缺少 False 返回值，与真实未启动线程不符；补全 fake 后 `lifecycle-unit-corrected.log` 16/16 通过，断言保留。最终完整检查已重新执行这些测试并通过。
- `startup-bind-failure-final/result.json` 原始脚本判失败，因为错误地在 stdout 查找异常文本；应用按既有日志策略把脱敏的 OSError / errno=48 写入生成目录日志。`oracle-review.json` 根据已保存的 `server_failed` 事件、退出码及后代退出证据复核通过；原失败不覆盖，应用未重跑，没有更改断言或业务代码来绕过。
- SIGKILL、宿主机终止、无法响应的浏览器及超出 150 秒宽限后框架强杀，均不在正常清理保证之内。本批不添加系统级 reaper 或全局进程匹配。
- 26 组此前归属未证实的历史浏览器仅核验登记 PID 身份，前后 26/26 身份一致，未发送信号；本批不替它们归属或清理。所有新服务的所有权由自有 Popen 后代链证明，端口和目录只作辅助证据。原工作区仍为干净的发布提交 `50d8b83`。
- 没有生产服务验证，也没有重新执行前轮全部 UI 性能、SQLite 和 347 项浏览器门禁。SQLite 修复仍仅为前轮测试夹具所有权修复，不扩大为生产连接泄漏修复结论。
